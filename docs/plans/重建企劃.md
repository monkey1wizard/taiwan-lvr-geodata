# taiwan-lvr-geodata 重建企劃

修訂日期：2026-10-07，Asia/Taipei。狀態：R-01 至 R-04 已完成並通過適用驗收。擁有者指示優先執行快速路徑 v2（全量輸出與循環作業文件，見重建任務卡），完成後接續 R-05。

本企劃定義接下來重做整個程式庫的範圍、目錄、工作順序與驗收條件。首個資料交付必須完成全部已盤點歷史來源的離線地址處理，不能以單季成果代替。

本文件是重建工作的唯一現行計畫，不另建立 .dev 副本或第二份語言版本。AGENTS 已更新計畫指向。舊企劃與操作文件已標示為歷史文件，舊驗收完成狀態不作新版依據。

## 一、已確定的要求

- 整個專案只保留最外層一個 `README.md`，子目錄不另設 README。此限制適用於專案維護的文件，不包含第三方套件或工具自行產生的檔案。
- README 是唯一入口，說明專案用途、實際資料範圍、下載與執行方式、目錄導覽及已知問題。
- 重做範圍包括程式分工、資料契約、命令入口、資料目錄、測試、文件與發布交接。每個舊模組都要判定保留並驗證、重寫、合併或淘汰。
- 一次啟動全歷史離線處理。程式可以內部分批、在失敗後接續，但全部選定來源處理完並通過驗收才算完成。單季只用於試跑或診斷。
- 承接 `C:/Code/taiwan-lvr-geojson` 已確認的補字規則、問題案例與證據。舊座標與舊地址鍵須重新驗證，不直接匯入為已定位。
- 修正 TGOS 地址錯配、地址重複與座標衝突。回傳成功不代表與送出地址相同，同一門牌號也不足以證明同址。
- 保留 `building_key_v2`、`validated_roc_to_tx_yyyymm` 與既有保留入口的相容契約。新舊介面共用核心規則，不各自複製一套。
- 在 `C:/Code/taiwan-lvr-geodata` 的 `main` 開發、測試、提交，再直接推送 `origin/main`。不建立開發副本、階段分支或 PR。GitHub Actions 負責 Linux 驗證。
- 安裝與自動測試只用合成資料，不下載真實資料、不需要憑證。真實全量驗收另列命令、輸入版本、結果與限制。
- 不推斷交易身分、修訂順序、子門牌等價、座標軸或來源權限。秘密、原始 ZIP、生成快照及第三方地址資料列不得進 Git。

## 三、範圍與方案選擇

採用「重新劃分模組與流程，逐項遷移並重新驗收」。只搬資料夾無法修正地址身分與驗收缺口。一次丟棄舊程式再重寫所有功能，則會失去既有規則、問題案例及相容行為。

保留經重新驗證的解析、日期、分批讀寫與輸出能力。地址身分、TGOS 採用條件、全量入口及成果管理須依新契約重整。沿用已鎖定的 Python、PyArrow、DuckDB 與 pytest 環境，沒有實測需要就不新增框架、常駐資料庫、分散式排程器或共用套件。

本次主體是 `taiwan-lvr-geodata`。舊 `taiwan-lvr-geojson` 作為唯讀參考，`taiwan-address-data` 作為固定版本輸入及後續補充資料接收端。全量離線處理不得依賴先修改地址專案。主專案先交付可驗證的地址新增／更新候選，地址專案的真實匯入與更新另記執行範圍及驗收。

既有 GitHub 公開、依交易月份下載、年度 ZIP 與無原始 ZIP 的維護交接需求繼續保留。線上資料庫載入與前端改版不納入這次重建。

## 五、主要流程與程式邊界

以下依 `gal:text-flowcharts` 的格式，將全量作業、單一地址與 TGOS 各步驟分圖表示。由上往下讀，只有判斷節點才分支。每條分支都標示結果，不把有先後關係的步驟畫成並列項目。

圖例：`(start)` 為輸入，`[ ]` 為處理，`{ }?` 為判斷。`(end √)` 表示完成，`(end >>|)` 表示保留或等待，`(end ×)` 表示拒絕或失敗。圖中的 `@模組` 對應目標程式分工，不代表該模組或命令已實作。

### 5.1 一次全歷史離線作業

```text
(start) 全部已盤點批次、固定地址來源與規則版本
  │
  ▼
{ 來源清單、雜湊及 ZIP 成員核對通過? }  @transactions.inventory
  ├── 否 ──▶ (end ×) 停止作業，保留前版及失敗原因
  │
  是，含已確認空批次
  ▼
[ 稽核全部地址基底，建立固定索引 ]  @offline.index
  │ 保留重複、無效及衝突證據
  ▼
[ 逐批解析，保留原文、來源位置及每列去向 ]
  │ @transactions.read / transactions.normalize
  ▼
[ 每個保留觀測的地址成員依 5.2 處理 ]
  │ 共用跨批次、跨類別地址池，不合併未證明相同的交易
  ▼
[ 彙整所有批次、地址狀態、排除及失敗紀錄 ]
  │ 未定位保留，部分成員定位另行標示
  ▼
{ 全部來源完成，筆數、關聯及資源驗收通過? }
  ├── 否 ──▶ (end ×) 不宣告全量完成，保留診斷與前版
  │
  是
  ▼
[ 產生交易月三格式、年度包、品質報告與維護包 ]
  │ @output.monthly / output.yearly
  ▼
{ 輸出一致性與無 raw 重產驗證通過? }  @output.verify
  ├── 否 ──▶ (end ×) 不更新公開指標，修復候選成果
  │
  是
  ▼
[ 發布全量離線版本，核對附件後更新指標 ]  @output.publish
  │
  ▼
(end √) 完成宣告範圍的離線交付，未定位池可進入 5.3
```

來源觀測、地址成員與唯一地址是不同粒度。已排除或失敗的來源列仍進入全量核對，不會因未進地址池而消失。單一地址完成不代表整次作業完成，必須等全部選定批次核對完畢才能發布。

### 5.2 一個地址成員的補字與離線定位

```text
(start) 一個保留觀測的地址成員
  │ 原始地址、來源列、規則版本、固定地址索引
  ▼
[ 套用已確認補字規則並拆解地址 ]  @addresses.characters
  │
  ▼
{ 仍含缺字? }
  ├── 否 ────────────────────────────────────┐
  │                                          │
  是                                         │
  ▼                                          │
[ 依路名及索引產生候選 ]  @offline.resolve     │
  │                                          │
  ▼                                          │
{ 唯一文字解，且有有效門牌證據? }               │
  ├── 否 ──▶ (end >>|) 保留原文與候選，待覆核  │
  │                                          │
  是                                         │
  ▼                                          │
[ 保存補正依據，重新拆解完整地址 ]              │
  │                                          │
  ├──────────────────────────────────────────┘
  ▼
{ 完整地址身分可確定? }  @addresses.identity
  ├── 否 ──▶ (end >>|) 地址待覆核，不猜門牌或子號
  │
  是
  ▼
[ 關聯全域地址鍵與原觀測成員 ]  @addresses.pool
  │ 同一有效鍵重用定位，原始觀測及出現關聯仍各自保留
  ▼
[ 查索引，核對同址證據及座標 ]  @offline.match
  │
  ▼
{ 定位結果? }  @results.reconcile
  ├── 有無歧義的有效證據 ──▶ (end √) 已定位，附採用證據
  ├── 衝突未解 ──▶ (end >>|) 保留全部證據，待覆核
  └── 無可用匹配 ──▶ (end >>|) 保留未命中或來源未涵蓋狀態
```

交易與地址來源使用同一套正規化及身分規則。完整門牌確定後才能移除樓層，主號、子號及無路名地址的村里身分必須保留。各結果都回到 5.1 彙整，未解地址不直接跳到 TGOS 送查。

### 5.3 一個 TGOS 批次的送出與匯入核對

```text

  │
  ▼
[ 重查候選地址及離線索引 ]  @tgos.batches
  │ 排除已定位、衝突、缺字及重複保留／送出的查詢
  ▼
{ 有完整未命中地址，且當日配額足夠? }
  ├── 否 ──▶ (end >>|) 保留原因及目前狀態，不自動送查
  │
  是
  ▼
[ 持久保存配額保留、批次與送出原文 ]  @tgos.batches
  │ 按共用帳號及服務日期計算
  ▼
[ 交付 CSV，等待人工上傳與提交確認 ]  @tgos.exchange
  │
  ▼
{ 操作員確認的提交狀態? }
  ├── 提交不明 ──▶ (end >>|) 保留配額，不自動重送
  ├── 尚未提交 ──▶ (end >>|) 等待確認或明確取消
  │
  已確認提交
  ▼
[ 等待人工下載，保存回傳原文與雜湊 ]  @tgos.exchange
  │
  ▼
{ 格式及原批次查詢集合精確一對一核對通過? }
  ├── 否 ──▶ (end ×) 拒絕採用該批次，保留原文與原因
  │
  是
  ▼
[ 逐列依 5.4 驗證，彙整全部結果 ]
  │ 相同批次與回傳雜湊重匯時，不新增證據副本
  ▼
(end √) 提交完整批次結果，可採用證據交給 5.5 與 5.6
```

5.1 的全量離線交付完成後，才能開始新的真實 TGOS 輪次。每日及每片上限沿用 10,000 筆，提交前取消才可依既有規則釋放保留。提交不明不能因逾時自動取消。既有回傳可先重新驗證，但不可沿用舊的「已定位」或「已驗證別名」結論。

### 5.4 一筆 TGOS 回傳能否採用

```text
(start) 已完成批次核對的一筆回傳
  │ 送出地址、回傳地址、原始座標及來源雜湊
  ▼
{ 座標及明確 CRS／軸向有效? }  @tgos.validate
  ├── 查無座標 ──▶ (end >>|) 保留未定位，不自動原樣重送
  ├── 無效或不明 ──▶ (end ×) 隔離，不猜測或互換座標軸
  │
  是
  ▼
[ 使用共用規則拆解送出地址與回傳地址 ]  @addresses.parse
  │
  ▼
{ 行政區、路段巷弄、主號、子號可證明同址? }
  ├── 否或有歧義 ──▶ (end >>|) 隔離，不定位原查詢地址
  │                            不自動建立已驗證別名
  是
  ▼
[ 保存證據，核對既有座標、來源及適用時間 ]  @results.evidence
  │
  ▼
{ 採用規則可作出無歧義決定? }  @results.reconcile
  ├── 否 ──▶ (end >>|) 保留衝突，不採用新定位
  │
  是
  ▼
(end √) 產生可採用定位證據，保留來源及採用依據
```

同址確認與座標採用是兩個判斷。TGOS 優先只能在同址確認後適用。座標表示觀測時的門牌位置，不自動證明歷史建物位置。人工覆核產生新地址表示或證據時，須重新經過地址判定及適用的離線比對。

### 5.5 一次有效定位狀態的歷史回補

```text
(start) 已提交的新定位狀態與前版完整成果
  │
  ▼
[ 回補全部適用歷史觀測 ]  @results.backfill
  │ 包含跨年、跨類別資料及無效證據撤銷的影響
  ▼
[ 重建受影響月檔與年度包 ]  @output.monthly / output.yearly
  │
  ▼
{ 回補、未變月檔及發布附件驗證通過? }  @output.verify
  ├── 否 ──▶ (end ×) 保留前版公開指標，記錄失敗並修復
  │
  是
  ▼
[ 發布新版並更新指標 ]  @output.publish
  │
  ▼
(end √) 完成全歷史適用範圍回補，最新未定位池再進入 5.3
```

每輪重新計算全歷史未定位池，已送出或失敗的相同查詢不會因建立新版而自動重送。一般使用者仍可使用先前完整發布的版本。

### 5.6 一筆有效證據的地址補充交接

```text
(start) 已確認同址且可採用的定位證據
  │
  ▼
{ 固定地址基底是否已有同址? }  @results.address_patch
  ├── 沒有 ──▶ [ 列為新增候選 ] ───────────────┐
  │                                            │
  已有                                         │
  ▼                                            │
{ 是否需要更新既有座標? }                        │
  ├── 否 ──▶ (end √) 只補充證據，不重複新增地址  │
  │                                            │
  是                                           │
  ▼                                            │
[ 列為更新候選，保存新舊差異 ]                   │
  │                                            │
  ├────────────────────────────────────────────┘
  ▼
{ 14 欄及必要行政代碼核對通過? }
  ├── 否 ──▶ (end >>|) 隔離缺欄位或有歧義的候選
  └── 是 ──▶ (end √) 交接可審查候選與來源證據
```

5.5 與 5.6 是有效證據的兩個用途，不是互斥分支。產生地址候選不代表地址專案已匯入。地址專案的基底重複、重複套用及官方更新保存能力仍須另行驗收。

### 5.7 模組責任

`pipeline.py` 決定階段順序與完成條件，`cli.py` 只解析參數。交易與 TGOS 模組共用 `addresses/`，不自行實作另一套地址鍵。離線與 TGOS 只產生可追溯證據，是否採用由 `results/` 統一決定。`output/` 僅讀取已提交的觀測與定位結果，不重新猜測地址。

`contracts/`、`storage/` 及地址純函式不得反向依賴命令入口。避免把每個現有檔案原樣套一層轉呼叫，也不為目錄完整而新增抽象介面。只為保留已盤點的舊介面建立必要相容入口。

現有 `contracts.py`、`tgos.py` 改為同名套件時，須在同一提交完成實作遷移，並由套件入口重新匯出已盤點的保留符號。TGOS 套件到 R-09 才切換，不提前建立會改變匯入解析的空套件。

## 六、必須重建的資料規則

### 6.1 全量、觀測與日期

- 本次全量基準為來源清單中的 58 批，含清單已記錄的已知空批次。執行前重新核對實體輸入與雜湊。新增來源時更新範圍版本，不在執行途中偷偷擴大。
- 區分來源清單完整、檔案存在、資料列處理完成及定位成功。缺失檔案不得當作空批次，全清單完成也不得宣稱官方歷史資料一定完整。
- `raw_record_id` 綁定來源雜湊、ZIP 成員及來源列位置。未證明交易身分時保留 `source_observation` 粒度，不依地址、金額、序號或批次順序自動合併交易。
- 每個輸入交易列都有保留、排除或失敗的明確去向。保留列可另有待覆核診斷。來源損壞或未完成分批不得以「有失敗清單」視為全量成功。
- `validated_roc_to_tx_yyyymm` 與固定截止年月決定交易月份。無效日期、土地、純車位與無門牌資料保留原因。地址成員展開不得重複計入交易金額。

### 6.2 補字與同址判定

- 分別保留原始地址、補正地址、拆解結果、地址鍵、規則版本及採用依據。保留 `building_key_v2` 名稱與相容介面，規則改變時另記正規化版本，不能以同名函式掩蓋快取失效。
- 私用區造字、字面問號、異體字、歷史行政區、重複行政區字首、路段數字與樓層各自有適用條件。不把全域字串替換當成同址證明。
- 完整門牌確定後才移除樓層。保留主號、全部子號、巷弄與無路名地址的村里／地名。門牌區間及縮寫無法無歧義展開時進覆核。
- 缺字候選須具有唯一文字解與有效門牌證據。多候選、同鍵多組未解座標及無法確認的字形均保留待查，不能任取第一個。
- 舊專案每項已確認修正都要對照新版結果。仍含缺字的輸入與舊定位成果用於查漏及證據核對，不直接整批匯入定位結果。

### 6.3 地址基底、座標與 TGOS

- 稽核固定地址基底的全部選定檔案。分開報告完全重複列、同址不同文字、同址不同座標及無法拆解地址，不以 `FULL_ADDR` 唯一作為未驗證前提。
- 保留原座標值、座標系與來源。比較小數精度及距離差異須先量測並記錄容許值，不以截短小數、距離接近或同一座標推定地址等價。
- 同址後才比較證據及來源優先順序。TGOS 優先原則僅適用於已確認同址且座標檢查通過的結果。未解的同等級衝突保留為衝突，不取首列、不平均座標、不默默覆寫。
- 座標表示來源觀測時的門牌位置，保存觀測時間及已知有效期間。門牌重編或重新指派時，依已確認的時間或別名證據判定適用範圍，不推定交易當時的建物位置。
- TGOS 送出前，以同一套規則重查全域地址池及離線索引。已定位、未解衝突、仍有缺字或已保留／送出的相同查詢不能自動再送。
- 沿用現有 addrCompare 人工操作條件、UTF-8-sig 五欄交換及每日／每片 10,000 筆限制。模糊查詢回傳只算候選，不是同址證據。座標軸與 CRS 不靠數值大小猜測。
- 共用帳號及服務日期的配額保留、提交不明、取消與重複匯入狀態須持久保存。提交不明不能因逾時自動釋放配額。舊查詢帳本可遷移，但舊已定位及別名結論須重新驗證。
- 回傳不符原地址時隔離，不得把回傳座標配給原查詢鍵，也不得自動建立已驗證別名。既有錯配須追查及撤銷其衍生採用結果，保留原始證據與更正紀錄。

| 核對結果 | 定位及地址補充處理 |
| --- | --- |
| 已確認同址，地址基底沒有該地址 | 座標及必要行政欄位驗證後列為新增候選 |
| 已確認同址，地址基底已有該地址 | 記為補充證據，座標需變更時另列更新候選，不偽裝為新增地址 |
| 行政區、路段巷弄、主號或子號不符 | 隔離，不定位原查詢地址，不新增自動別名 |
| 文字不同但等價證據不足 | 保留候選與原因，待覆核 |
| 同址但座標無效、軸向不明或衝突未解 | 保留證據及衝突，不採用新定位 |

地址補充保留現有 14 欄 CSV 契約，來源證據另存。行政代碼缺失或有多解時隔離。地址專案真實合併前需完成全基底重複稽核及衝突決策，不能只檢查這次 patch 碰到的路檔。官方更新不得默默丟失已核准補充。

### 6.4 執行、輸出與復原

- 每次執行的 manifest 固定程式、輸入、地址來源、規則、契約版本及截止年月。只有相同綁定且檔案重新核對通過的階段可以續跑。改動任一綁定就建立新執行，不混用舊結果。
- 每次執行各自保存暫存檔。完整驗證後才提交階段清單，讀取端不使用半成品。完成的資料檔不可原地改寫，TGOS 回補建立新的結果版本。
- 用單一寫入鎖或等效排他機制保護目前指標與 TGOS 配額。程序中斷、過時寫入者或磁碟不足時，前版仍可讀取。
- 測試暫存使用系統暫存目錄。清理前列出用途、重建方式、引用關係與可刪條件。原始 ZIP、人工回傳、未遷移證據及現行成果不得當成快取清除。
- 月份依 `tx_yyyymm`，保留 `YYYYMM_category` 名稱與 sales、presale、rent。GeoParquet、GeoJSON、NDJSON 的識別、屬性、筆數與 null 幾何一致。全未定位觀測仍保留。
- 保留現行 Point／MultiPoint／近似 bbox Polygon 契約，防止零面積 Polygon，明確標示近似及部分成員定位。不得把 bbox 說成建物輪廓。
- GIS 屬性契約（2026-10-08 擁有者核准）：三種格式的月檔最外層都要有可直接分析的欄位：`trade_date`（ISO 日期）、`county`、`district`、`address`、`building_type`、`total_price`（元）、`unit_price_sqm`、`building_area_sqm`、`location_status`，以及單一點位時的 `longitude`、`latitude`。來源沒有值時為 null，不補 0。`props_json` 保留供追溯。
- 年度點位檔（2026-10-08 擁有者核准）：每年每類別一個 CSV，例如 `yearly/2024/2024_sales_points.csv`，UTF-8 不加 BOM，只收完整定位且單一點位的觀測，欄位同上並保留 `raw_record_id`。供 Kepler.gl 等 GIS 工具直接載入，登記於 manifest 並由輸出驗證核對筆數與雜湊。
- 年度 ZIP 包含同一版本的原月檔位元組。缺月、空月、部分年度與來源涵蓋分開標示。回補只更新受影響月份及年度包，其他資料檔雜湊不變。
- 全量月檔、年度包及維護包均須量測附件大小並核對發布平台限制。必要時分片並保留完整索引，維持原本的月／年邏輯單位及無原始 ZIP 重產能力。
- 發布候選與維護包先驗證，再更新公開指標。既有公開版本保持可取得。維護包須足以在無原始 ZIP 的乾淨 Linux 環境重產相同月檔並接續 TGOS。
- 保存來源條件及顯名，不自行推定來源權限，也不把舊文件中已被取消的上游權威證明門檻重新加入流程。

## 八、工作順序與交付

### 8.1 快速資料路徑例外（2026-10-06 擁有者決定）

擁有者決定先取得全歷史資料及 TGOS 送查檔，因此在 R-03～R-08 之前先執行一次快速路徑。這是對「R-08 完成後才開始新 TGOS 輪次」的單次例外，其他順序不變。

- 以現有命令處理基準清單全部 58 批，結果標示為「快速版，非驗收」，不作為 V-08～V-11 的通過依據。
- 新輪次只允許產生送查檔及送出。TGOS 匯入只採用回傳地址與送出地址 `building_key_v2` 相同的結果，其餘隔離，不建立別名。這是 R-09 同址判定的最小保守版本。
- 舊批次 `p3-tgos-20261005-001` 的查詢帳本帶入新狀態，避免重送。舊匯入結果、證據及別名不帶入，回傳原文須依新規則重新匯入。
- 原始資料若有引號未閉合等無法嚴格解析的檔案，改以逐行解析。無法解析的行記為失敗並保留原文，報告列出改用逐行解析的檔案。

### 8.2 TGOS 日期紀錄更正（2026-10-07 擁有者決定）

TGOS 日期不是地址批次限制，也不參與地址挑選、批次識別、提交狀態或匯入判定。日期獨立記錄在 `data/tgos/date.json`，最多只用於資料夾或檔案名稱。交換資料夾固定使用 `data/tgos/YYYYMMDD-<識別碼>/`，例如 `data/tgos/20261007-0358ee6e90df/`。交換檔可先交由其他人協作上傳，不得因紀錄日期尚未到達而禁止提交。第五節及第六節中按服務日期保留配額的舊設計由本節取代。每個交換檔仍以 10,000 筆為上限，實際帳號使用量由操作流程另行核對。

既有 TGOS 候選與地址 patch 在重新驗證前不得作為新版有效輸入或繼續發布。R-09 可先做不涉及真實新查詢的修復，但新的 TGOS 輪次必須等 R-08 的全量離線交付完成。人工 TGOS 尚未返回時保留等待狀態，不阻擋已完成的離線成果使用。
