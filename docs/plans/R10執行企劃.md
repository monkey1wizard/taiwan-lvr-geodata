## R10-1a 第二類人工查核區

**接法。** R09-8 會在 `offline-state` 之後新增 `tgos-state` 階段，並讓 review 讀它。R10-1a 在 `build_review` 內建立 `second_review.parquet`、`second_review_observations.parquet` 與同名 CSV，規格見[資料契約](../資料契約.md)「第二類人工查核區」。`run-full` 新增 `--review-decisions <目錄>`，預設 `data/review-decisions/`。目錄下全部判定檔的檔名與 SHA-256 清單寫入 review 階段綁定，所以新增判定檔會使 review 與之後的階段重建。

**進入原因代碼。** 新增 `tgos_not_found`、`tgos_key_text_not_round_trip`、`district_no_candidate_town` 三個代碼，加入 `EXCEPTION_REASON_CODES`。文字算不回鍵的門牌目前只在 `prepare-tgos` 計數，R10-1a 要在 review 建置時以同一函式重算，不能讀 `prepare-tgos` 的報告。缺區無候選區也一樣重算。

**回傳門牌鍵。** R09-7 第 1 批的 3,640 筆地址不符列在帳本中 `response_building_key` 全部為空，見 [V-12 裁定分析](../records/V-12裁定分析.md)。建置時以現行 `building_key` 從 `response_address` 重算，算不出時欄位為空並保留原因。

**判定檔核對。** 依契約的冪等與核對規則：檔名雜湊不符拒絕，同檔重複查核鍵拒絕，`orphaned` 與 `stale` 不套用並計數。`accept_tgos_response` 要核對 `tgos_result_id` 屬於該查核鍵且回傳座標通過範圍檢查。`manual_coordinate` 要核對經緯度範圍。

**陷阱。** 判定檔是擁有者證據，程式只讀不寫。測試用合成判定檔放在 `tests/` 的暫存目錄，不寫入 `data/review-decisions/`。

**驗收。** 合成案例：每個進入原因各一列、等待中的查詢不進入、`located` 不進入、`conflict` 進入但暫停縣市不進入、三種判定各一、同檔重複查核鍵拒絕、檔名雜湊不符拒絕、`orphaned`、`stale`、同一組判定檔重跑結果不變、較晚判定取代較早判定。全套 pytest 通過。

## R10-1b 回補與受影響月份

**名詞。** 回補指把 TGOS 採用與人工 `adopted` 判定的座標放進公開輸出。依 10-12 決定，回補只新增列。經新規則核驗的 TGOS 或人工查核結果可更新既有列的地址與座標。

**接法。** 新增 `final-state` 階段，位於 review 之後、output 之前。它以 offline-state 為底，加上 tgos-state 的採用結果與 review 的 `adopted` 判定，產生 output 要讀的定位結果與 `coordinate_sources.parquet`。output 改讀 `final-state`，`output_id` 的雜湊輸入加入 `final-state` 的 manifest。若 R09-8 已讓 output 直接讀 tgos-state，R10-1b 改為在同一入口加入人工判定，不重做 R09-8 的部分。施做前先讀 R09-8 的實際提交。

**來源優先序。** 同一門牌同時有 TGOS 採用與人工 `adopted` 時，先後順序未定，見「待釐清事項」1。決定之前，兩者座標不同時不採用任何一方，記 `conflict` 並列入第二類人工查核區。

**受影響月份的判定。** 比較基準是上一個公開版本的 `final-state`，第一次回補時則是 offline-state。

1. 找出定位結果有差異的門牌鍵：新增定位、座標改變、代表地址改變。
2. 經地址成員找出這些門牌鍵的全部 `transaction_id` 加 `door_index`，再取每列的 `tx_yyyymm` 與 `category`。
3. 受影響檔案為這些年月與類別的每月 CSV，加上 GeoParquet 單檔與 `catalog.json`。
4. 受影響清單寫入 `data/runs/<run-id>/review/affected_months.json`，含每個年月與類別的新增列數與更新列數。

**未受影響月份雜湊不變的證明。** 一律重產全部輸出，不只寫受影響月份，因為全部重產也同時檢驗輸出的確定性。R07-12e 已證明同一輸入兩次輸出雜湊相同。比較新舊 `catalog.json` 的逐檔項目：

- 不在受影響清單的檔案，`sha256`、`rows`、`size_bytes` 必須全部相同。
- 在受影響清單的檔案，新列數減舊列數必須等於清單記錄的新增列數。
- 受影響清單有、但雜湊沒變的檔案列為警告並說明原因。
- 比較程式寫在 `lvr_pipeline/output/` 或 V-13 腳本，結果存 `data/tmp/v-13/`。

**陷阱。** 比較基準與新 run 必須是同一程式指紋。R09-9 用新的距離精度重跑，所有月份都可能改變，那是新基線，不是回補，不能用來證明未受影響月份不變。

**驗收。** 合成 `run-full`：無判定、一個 `adopted` 判定、一個新增 TGOS 採用，三種情況各跑一次。斷言受影響清單正確、未受影響每月 CSV 雜湊不變、`coordinate_sources.parquet` 列數等於更新門牌的觀測數。全套 pytest 通過。

## R10-2 邊界情況

| 情況 | 規格 | 合成案例 |
| --- | --- | --- |
| 跨年跨類別 | 一個門牌鍵同時出現在不同年月、不同類別。採用後每個年月與類別都列入受影響清單 | 同鍵出現在 2015 年買賣與 2024 年租賃 |
| 門牌重編 | 舊門牌與現行門牌沒有證據就不連結。舊門牌查無時留在第二類人工查核區，不以新門牌座標代替 | 舊號在地址來源不存在，TGOS 回傳新號 |
| 別名撤銷 | 快照中有 `verified_aliases` 與 `alias_events`。別名撤銷後，經該別名定位的門牌不再定位 | 撤銷前後各跑一次 |
| 晚到回傳 | `submission_unknown` 批次的回傳較晚交回時照常匯入。同一查詢較晚的成功結果與先前座標不同時，依 `validate.py:350-352` 記 `conflict` | 同查詢先查無、後成功，以及先成功、後不同座標 |

別名撤銷會使已發布的列消失，與「回補只新增列」不一致，見「待釐清事項」2。決定之前，R10-2 只實作偵測與報告：撤銷影響的列寫入 `affected_months.json` 的 `removed` 計數，回補失敗並停下，不自動刪列。

**驗收。** 上表每個案例都有測試，受影響月份與新舊狀態符合證據。沒有證明地址等價時保留隔離。全套 pytest 通過。

## V-13 回補驗收

以真實資料執行一次回補，紀錄放 `docs/records/V-13回補驗收.md`，腳本與產物放 `data/tmp/v-13/`。

1. 回補關聯：`coordinate_sources.parquet` 每列都對應到輸出中存在的 `transaction_id` 加 `door_index`。每個 `adopted` 判定恰好套用一次。
2. 版本差異：新舊 `catalog.json` 的逐檔比較，新增列數與更新列數分別等於受影響清單。
3. 受影響輸出：有變化的檔案集合等於受影響清單的檔案集合，或差異已列為警告並說明。
4. 未受影響雜湊：清單外的每月 CSV 雜湊、列數、大小全部相同。
5. 冪等：同一組判定檔重跑一次，`output_id` 與全部檔案雜湊相同。
6. 計數：`orphaned`、`stale` 判定數，以及第二類人工查核區各進入原因的列數。

## R10-3 新 TGOS 輪次

**送查集合。** 從最新的未定位池選取：`unmatched` 中尚未送查的門牌鍵、R09-8 修正規化後可以算回原鍵的門牌、第二類人工查核區中狀態為 `pending` 或 `deferred` 的查核鍵。`rejected` 不選。`conflict` 依 10-17 決定 4 不送。`submission_unknown` 不重送。

**核准重送的規模問題。** 查無的回傳列狀態是 `failed`，已在可重送狀態內，但每個指紋都要一個 `--retry-query-fingerprint` 旗標。第 1 批就有 3,551 筆查無，逐筆放進命令列不可行，命令列也不保存核准清單本身。

| 方案 | 做法 | 優點 | 缺點 |
| --- | --- | --- | --- |
| A 重送清單檔 | 新增 `--retry-file <CSV>`，每列一個 `query_fingerprint`。清單由唯讀腳本從第二類人工查核區產生，檔案 SHA-256 與 `--retry-reason` 寫入批次紀錄 | 核准範圍明確、可稽核、可重算 | 需要多一個檔案與產生步驟 |
| B 依規則選取 | 新增 `--retry-entry-reason tgos_not_found` 等條件，由程式選出全部符合的指紋 | 命令最短 | 核准範圍隱含在程式裡，條件寫錯會一次重送大量門牌 |
| C 只重送文字改變的門牌 | 只有送查文字與上次不同時才可重送，例如 R09-8 修正規化後 | 不浪費查詢名額 | 查無但文字沒變的門牌永遠不會重送 |

建議採 A，並加上 C 的檢查作為報告：清單中送查文字與上次相同的筆數寫入報告，由擁有者決定是否仍要重送。理由：同一文字重送，TGOS 很可能回傳相同結果。單檔上限 10,000 筆，3,551 筆可放進一批。超過時分批，每批各自記錄清單檔雜湊。

**驗收。** 合成案例：清單檔重送、清單含不可重送狀態時整批拒絕、`rejected` 判定不被選、`submission_unknown` 不被選、清單雜湊寫入批次紀錄。真實輪次另有紀錄，含送查集合、帳本、提交狀態、回傳雜湊與匯入結果。

## 陷阱

- 不得在 V-12 判定之前改變村里或鄰的比對規則。306 筆只差村里或鄰的回傳，在擁有者裁定前都依現行規則拒絕，可以進入第二類人工查核區。
- 判定只決定座標與代表地址，不改 `building_key`、不合併門牌鍵。異體字或村改里即使經擁有者採用座標，兩個鍵仍是不同門牌。
- 不得刪除 tgos-state 中間快照或 `data/tgos/` 交換證據，也不得修改 `data/review-decisions/` 中已寫入的判定檔。
- `data/runs/` 的基線 run 只讀。回補使用新的 run ID。
- 合成測試若因新檢查失敗，改用正確夾具，不加繞過旗標。
