## 施做前必須知道的程式事實

行號以 `f794bdf` 為準。

### 快照與驗證流程（`lvr_pipeline/storage/runs.py`、`storage/parquet.py`）

- `SnapshotStore.add`（runs.py:184）：複製檔案、`_inspect` 逐列驗證、SHA-256，然後整份重寫並 fsync `draft.json`。讀入階段約 349 個檔、正規化約 1,045 個檔，所以 `draft.json` 重寫成本隨檔數平方成長。
- `_inspect` 呼叫 `inspect_parquet`（parquet.py:79）：每個 batch `to_pylist()`，每列 `json.loads` JSON 欄、`validate_rows`（contracts/validate.py:45）jsonschema 驗證、觀測重算 `observation_id` 與日期規則、已確認的地址元件重算 `building_key`。這是逐列 Python，是耗時主因。
- `publish`（runs.py:285）：`verify(staged, draft=True)` 一次，改名後 `verify(final)` 再一次。`_verify`（runs.py:240）重做 SHA-256、`_inspect` 與 DuckDB `verify_relations`（parquet.py:156）。
- `RunStore.commit`（runs.py:389）再 `verify` 一次；`load_snapshot`（runs.py:503）每次下游載入都 `verify`；`reusable`（runs.py:318、403）續跑判斷也 `verify`。`export_converted`（converted.py:28）另跑一次 `verify_relations`。
- 合計：一個快照在建立時被逐列驗證約 4 次，每個下游階段載入再 1 次。converted 被 coverage、address-pool、review、output 各載入一次。
- `checkpoints.json` 已記每階段的 `manifest_sha256` 與 `snapshot_id`（runs.py:396、413）。manifest 內有每檔大小與 SHA-256。12b 要利用的就是這些既有欄位。

### 快照 ID 與綁定

- `bindings`（runs.py:452）把所有 `lvr_pipeline/*.py` 與 `uv.lock` 的雜湊納入 `config_sha256`，快照 ID 為 `{kind}-{digest[:24]}`。任何程式修改都會改變全部快照 ID，所以 R07-12 之後 `r07-10-20261014b` 的快照不能沿用，R07-10 必須以新 run ID 全量重跑。
- `PRODUCER_CONFIGS`（runs.py:422）是每個程序各自的 dict，由 `bindings` 填入，`Stage.finish`（runs.py:484）讀它。多程序時子程序若沒先呼叫 `bindings` 就 `finish` 會 `KeyError`。12d 要處理。
- `RUN_BINDING_KEYS`（runs.py:325）是 run 綁定的固定鍵集合，新增鍵要同步改測試夾具。
- 下游綁定吃上游 manifest 雜湊，而 `quality.json` 含耗時、RSS 等非決定性欄位且屬於 manifest，所以兩次獨立 run 的下游快照 ID 必然不同。12e 比對時要排除這些欄位，或只比對資料檔雜湊。

### `run_full` 流程（`lvr_pipeline/pipeline.py`）

- `run_full`（pipeline.py:390）順序：`rebuild_source_failures` 與 `admin_towns_failures` 檢查（:407、:411）→ 磁碟餘裕 → `.run-full-lock`（:544）→ `verify-sources` → `offline-index` → `ingested` → `normalized` → `converted` → `coverage`（:573，會 `load_snapshot(converted)`）→ `address-pool` → `offline-state` → `review` → `output` → run report。
- `stage()`（pipeline.py:434）包每個階段：磁碟餘裕檢查、`reusable` 續跑判斷、執行、`commit`、記 `elapsed_seconds` 與 `process_peak_rss_bytes`（:450）。它修改 `current` 與 `result["steps"]`，沒有鎖。
- `peak_rss_bytes` 是單一程序的峰值。多程序後必須改為合計，否則 V-10b 的 RSS 證據失真。
- run report 的 `duckdb_memory_limit`（:458）只記環境變數。
- `RunStore._lock`（runs.py:371）遇到競爭直接拋 `RuntimeError`，不等待。

### 釘選檢查

- `load_pinned_source`（offline/index.py:86）：`git rev-parse HEAD` 必須等於描述檔 `commit`，`git status --porcelain` 必須為空，然後回傳 `AdministrativeNames`，它會核對行政區表雜湊（offline/match.py:27）。
- 呼叫位置：`build_index`（index.py:169、316、377、441）與 `build_pool`（addresses/pool.py:119、276）。`build_pool` 在 `load_snapshot(converted)` 之後才檢查，所以第二次試跑在失敗前多跑了約 28 分鐘。
- 路名檔雜湊目前在 `build_index` 讀檔時核對（index.py:102 一帶）；`char_fixes.csv` 雜湊在 `addresses/address_fixes.py` 的 `load_address_char_fixes` 核對；`admin_towns.json` 由 `admin_towns_failures` 對描述檔核對。

### DuckDB 與資源

- `duckdb_config`（parquet.py:130）讀 `LVR_DUCKDB_THREADS`（預設 2）、`LVR_DUCKDB_MEMORY_LIMIT`（預設 256MB）、`LVR_DUCKDB_TEMP_LIMIT`（預設 1GiB）。上限是每個連線各自計算。`config/pipeline.example.toml` 的 `duckdb_*` 欄位程式不讀。
- 擁有者決定全量 run 用 `8GiB`、`64GiB`、`4`。第二次試跑最高 RSS 3.59 GB。
- 機器：61.6 GB RAM、24 邏輯 CPU、C: 約 700 GB 可用。磁碟餘裕要求 20%（pipeline.py:365）。

### 輸出的決定性

- 列的身分都由內容或位置算出（`observation_id`、`component_id`、`evidence_id`、`transaction_id`），不靠序號；讀入、正規化、occurrence、offline-index 的檔案列順序是寫入順序，其他階段有 `ORDER BY`。
- Parquet 位元組取決於 `BatchWriter` 的 flush 邊界（parquet.py:21 一帶，`batch_rows` 與 8 MiB 預算）。平行時同一段程式寫同一個檔才能保持相同。
- `output/gpkg.py:93` 的 `_now()` 寫入時間戳，GeoPackage 位元組本來就不可重現；12e 比對時排除。
- `output/build.py:21` 的 `_Open` 要求列依 `trade_date` 順序到達，否則拋錯；`output/rows.py:240` 的 `ORDER BY` 提供這個順序。GeoParquet 排序規格在 `docs/輸出欄位.md:69`。
