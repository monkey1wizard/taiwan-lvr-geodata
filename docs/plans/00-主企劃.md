# 00 主企劃：全歷史實價登錄門牌座標重建

修訂日期：2026-10-18，Asia/Taipei。這份文件講整個專案的大架構、三個里程碑、現在走到哪、誰手上有事，以及全部工作。工作分三大類：類別 i 是送出下一批 TGOS 前必須完成的，類別 ii 是送 TGOS 並依結果逐漸修改的，類別 iii 是不論 TGOS 情況都能持續做的。i 與 iii 可以同時進行。任務編號是段落字母加兩位數，例如 `a01`、`b02`。工作量大的段落另有子企劃檔：A、B、C、D。規則的權威內容在[地址規則](../地址規則.md)、[資料契約](../資料契約.md)、[輸出欄位](../輸出欄位.md)。所有有效擁有者決定、驗收狀態與證據索引在[擁有者決定與驗收總表](擁有者決定與驗收總表.md)。

## 一、目標

把內政部實價登錄從 2011 年至今的每一筆交易門牌配上經緯度，公開成每月每類別的 CSV 與一個 GeoParquet 檔。配座標有兩條路：先用固定版本的地址資料庫離線配對，配不到的再送內政部 TGOS 門牌定位服務查，TGOS 也查不到的交給擁有者逐筆判定。

## 二、系統架構

### 資料怎麼流

```text
(start) 一筆交易門牌，來自 58 個原始 ZIP 之一
  │  讀入 → 正規化 → 轉換 → 地址成員          @run-full
  ▼
{ 能產生門牌鍵? }                              @building_key
  ├── 否，區名錯或區間地址 ──▶ (end ×) 待查核表 invalid_admin
  ├── 否，只缺區 ───────────▶ [ 缺區查詢 ]  @prepare-tgos ── 併入下方送查
  │
  是
  ▼
[ 地址池 → 離線索引 → 離線定位 ]               @run-full
  │
  ▼
{ 離線配得到? }                                @adopt_coordinates
  ├── located  ──▶ (end √) 進輸出：每月 CSV、GeoParquet
  ├── conflict ──▶ (end ×) 待查核表，依決定不送 TGOS
  │
  unmatched
  ▼
[ 產生送查檔 ]  @prepare-tgos   帳本記下查詢原文，不重送
  │
  ~~▶ 擁有者每天上傳一批、拿回 Address_Finish.csv
  ▼
[ 匯入回傳 ]  @import-tgos      帳本記回傳原文與雜湊
  │
  ▼
{ 回傳是同一個門牌? }           @same_door，C 段加村里代碼與鄰規則
  ├── 是 ──▶ (end √) 採用座標，經回補進輸出      D 段 @final-state
  ├── 查無 ────────────┐
  ├── 回傳別的門牌 ────┤
  └── 村里鄰或座標不符 ┘
                       ▼
                     [ 第二類人工查核區 ]   D 段 @second_review
                       │
                       ~~▶ 擁有者逐筆判定，判定檔跨 run 沿用
                       ▼
                     { 擁有者判定? }
                       ├── adopted  ──▶ (end √) 採用座標，經回補進輸出
                       ├── deferred ──▶ (end >>|) 留到下一輪 TGOS
                       └── rejected ──▶ (end ×) 不定位，保留原因
```

讀法：一個門牌從最上面掉下來，`{ }` 是分岔，`(end √)` 是拿到座標進輸出，`(end >>|)` 是刻意延後，`(end ×)` 是走不下去。每次全量重跑都會把帳本裡的回傳用當時的規則重新判定一次。標 B、C、D 段的格子尚未實作：帳本接進 `run-full` 由 B 段做，採用規則由 C 段做，第二類人工查核區與回補由 D 段做。

### 四個速度不同的迴圈

| 迴圈 | 速度 | 性質 | 跨迴圈留下什麼 |
| --- | --- | --- | --- |
| 離線流程 `run-full` | 約 2 小時 | 確定性。規則或程式改一個字就要整個重跑，產生一個新 run | run 目錄與輸出。通過驗收並發布的那個 run 叫基線 |
| TGOS 交換 | 每天一批，不可逆 | 外部服務。送出的查詢文字與回傳都是證據 | 帳本：查詢原文、批次、回傳原文、雜湊。每次新 run 以當時規則重新解讀同一份回傳 |
| 人工判定 | 以週計 | 擁有者逐筆判定 TGOS 後仍無座標的門牌 | 判定檔，跨 run 沿用 |
| 發布 | 以版本計 | 某個 run 的輸出快照 | 第一版、第二版。晚到的回傳與判定經回補成為增量更新 |

### 三條原則

1. **規則定稿在前，配額在後。** 查詢文字由規則產生。規則改了，已產生未送出的批次作廢要重產，已送出的永久留在帳本。所以會改門牌鍵或查詢文字的修正，都要在送出前做完。這就是類別 i 的定義。
2. **TGOS 回傳是不可變證據，解讀隨規則版本。** 採用與否在每次 run 重新判定。採用規則改了不必重送。這就是為什麼類別 ii 可以邊送邊改。
3. **輸出按 run 版本化，晚到的證據走回補，不走重送。** 任何程式修改都使之前 run 的指紋失效；下一次發布前全量重跑並重做 V-10b 與 R08-2a 即可。這就是為什麼類別 iii 不必等 TGOS。

| 名詞 | 意思 |
| --- | --- |
| 基線 | 通過驗收並發布的那一次全量 run。目前是第一版的 `r07-10-20261016b` |
| 過渡基線 | B 段為了重產送查檔而跑的一次 run，不發布，不重做發布用的驗收。目前是 `b16-20261018b` |

| 第二版 | 加上 TGOS 回補座標的公開資料 |
| 第二類人工查核區 | TGOS 也查不到的門牌，等擁有者逐筆判定的集合 |

## 九、工作方式

- 在 `main` 修改、本地驗收、本機提交。不推送、不建分支或 PR。
- 每張程式卡完成要有：全套測試通過、從[空白範本](../task-result-template.md)複製的驗收紀錄、受影響文件同步、本機提交、本文件或子企劃的核取方塊打勾。
- 真實資料命令一律設 `LVR_DUCKDB_MEMORY_LIMIT=8GiB`、`LVR_DUCKDB_TEMP_LIMIT=64GiB`、`LVR_DUCKDB_THREADS=4`。
- `data/runs/` 下的基線與 TGOS run 目錄只讀。檢查產物放 `data/tmp/<purpose>/`。
- 同時進行的 session 提交只用 `git add <明確路徑>`，改本文件或總表前先 `git diff` 確認乾淨。
- 正式文件不超過 550 行。舊企劃原文在 git 歷史，提交 `c3f1284` 之前。
