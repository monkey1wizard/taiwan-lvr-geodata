## 一、執行者共通規則

每張任務卡都適用以下規則，卡片內不再重複。

1. 開工前讀本節、該卡片，以及卡片「依據」欄列出的企劃章節。不需要讀整份企劃。
2. 只做卡片列出的變更。發現卡片以外的問題時，記入工作紀錄的「下一步」，不要順手修。
3. 搬移程式時，行為保持不變。先搬移、跑測試、提交，再另開提交修改行為。
4. 卡片標示 **停下回報** 的情況出現時，停止修改，在工作紀錄寫明現況與選項，然後回報擁有者。
5. 以下情況一律停下回報：
   - 測試預期值需要改動才能通過。
   - 需要判斷交易身分、修訂順序、子門牌等價、座標軸或來源權限。
   - 需要下載真實資料、刪除 `data/` 內任何檔案，或對外發布。
6. 每張卡至少執行一次完整測試：`.venv/Scripts/python.exe -m pytest -q`（Windows，約 4 分鐘）。
7. 每張卡一個提交為原則，在 `main` 提交後直接推送 `origin/main`。推送後用 `gh run list --limit 1` 及 `gh run watch` 確認 Linux CI 結果，並把 run 編號寫入紀錄。程式提交要先單獨推送並確認 CI，之後才推送帶 `[skip ci]` 的紀錄提交。兩者一起推送時，GitHub 只看最新提交的訊息，會跳過整次推送的 CI。要觸發 CI 的提交，訊息任何位置都不能出現這個標記字串，說明文字也不行。
8. 工作紀錄按工作包合併：同一個 R 編號的所有卡片寫在同一份 `docs/records/R0X執行紀錄.md`。第一張卡從 `docs/task-result-template.md` 複製建立，後續卡片在「命令與結果」表追加列。
9. 卡片完成不等於工作包驗收。只有標為「驗收卡」的卡片可以寫 V 編號通過，而且必須附命令輸出證據。
10. 規劃者在每一輪卡片完成、核對提交與 CI 之後，更新第三節進度總表。卡片內容與實際程式不符時，同時在卡片內註明更正日期與原文。執行者不改進度總表。
11. 檢查、驗證、診斷、查核用的輸出，以及失敗後需要保留的產物，一律放在 `data/tmp/<用途>/`，例如 `data/tmp/handoff-check/`、`data/tmp/review/`、`data/tmp/kepler/`。`data/raw/`、`data/cache/`、`data/tgos/`、`data/output/` 只放符合企劃第四節目標布局的資料。（擁有者 2026-10-08 指示）

### R03-12 舊規則版本的快照無法通過驗證（規劃者 2026-10-07 新增）

- 方向：驗證地址成員時，依快照綁定中的 `normalization_version` 判斷。版本與目前程式相同時重算鍵；不同時只核對檔案雜湊與結構，並在回報中標示「舊規則版本，未重算鍵」。舊快照不可被當成可重用結果。
