## 起因

R07-10 第三次 run `r07-10-20261015b` 的前 7 階段完成後，output 階段失敗兩次，見 [R07-10 執行紀錄](R07-10執行紀錄.md)：

- DuckDB 上限 8 GiB 時約 120 s 後 `OutOfMemoryException`。
- 擁有者同意只對該次續跑提高到 24 GiB 後，跑了約 2.5 小時沒有寫出任何列，CPU 大致只用一個核心，擁有者決定中止並改寫查詢。

原因：`lvr_pipeline/output/rows.py` 的 `iter_door_rows` 以單一查詢處理全部約 440 萬筆觀測，含視窗函數 `door_count`、三個明細 `list()` 彙整與對寬欄位的全量 `ORDER BY`。溢寫目錄用 `tempfile.TemporaryDirectory`，位於系統 `%TEMP%`。

## 實作

- `rows.py`：分區鍵 `_PARTITION_KEY = "left(tx_date_raw, 5)"`，即民國年三位加月兩位。先取不重複分區鍵 `ORDER BY k NULLS LAST`，每個分區執行一次查詢：先把觀測篩成 CTE `ob`，元件與三種明細只取 `ob` 內的 `raw_record_id`，SELECT、join、`door_count` 視窗與 `ORDER BY` 不變。舊的單一查詢已刪除。
- 分區正確性：字串前綴在字典序下單調，若 a ≤ b 則 a[:5] ≤ b[:5]，所以依分區再依完整排序，與直接依完整排序得到相同序列，格式錯誤的日期也一樣。`NULLS LAST` 與舊查詢的 DuckDB 預設一致。`build.py` 以 `roc_date(tx_date_raw)` 取月份，需要 7 位數字，前 5 位就是年月。
- 日期無效的列仍會在某個分區輸出，`write_output` 照樣以「no valid trade_date」拒絕。正規化已排除日期無效的列，真實資料不會出現。
- `output/build.py`：`write_output` 新增必填 `spill_dir`，刪除沒有使用者的 `order_by` 參數。
- `pipeline.py` 輸出階段把溢寫目錄設在 `<run>/output/build/spill-<output_id>`，在輸出目錄之外，結束後刪除。
