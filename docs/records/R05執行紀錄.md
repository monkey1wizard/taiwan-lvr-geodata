## 結論與限制

R05-1 為純搬移，函式本文、簽名與行為未改；只有匯入路徑與模組位置改變。真實資料驗收、公開發布、跨專案匯入均未執行。

搬移對照：

| 舊位置 | 新位置 |
| --- | --- |
| `address_source.py`（`ADMINISTRATIVE`、`METADATA`、`_git`、`pin_address_source`） | `offline/index.py` |
| `offline_lookup.py`：`load_pinned_source`、`build_index` | `offline/index.py` |
| `offline_lookup.py`：`COUNTY_NAMES`、`AdministrativeNames`（含 `canonicalize`） | `offline/match.py` |
| `address_state.py`：`load_p2`、`resolve_offline` | `results/reconcile.py`（新套件 `results/`） |

比對函式的分法：`match.py` 只放把地址文字對到行政區代碼的名稱比對（`COUNTY_NAMES`、`AdministrativeNames`）。`index.py` 保留從固定地址來源建索引、固定來源與載入的程式。`index.py` 由 `match.py` 匯入這兩個符號。`resolve_offline` 隨 `address_state.py` 整檔移入 `reconcile.py`，沒有拆出。

程式指紋範圍：`storage/runs.py` 的 `bindings()` 原本涵蓋 `lvr_pipeline/*.py` 與 `addresses/`、`offline/`、`storage/`、`contracts/` 目錄。`results/` 不在其中，因此比照 R04-1、R04-7 加入 `results/*.py`。搬移與納入使程式指紋改變，屬預期結果。

保留相容符號：`tests/compatibility/` 只涉及 `address`、`contracts`、`tx_date` 與 `cli` 子命令，未涉及被搬移的模組；不留轉址檔。已改匯入的檔案：`address_pool.py`、`packaging.py`、`pipeline.py`、`tgos.py`、`scripts/measure_admin_parse.py`、`tests/integration/test_p2_offline.py`。

只查因，未修改。分類結果在 `data/tmp/r05-8b/invalid_admin_with_key.txt`（讀 `../taiwan-address-data` 固定提交 `3ff9be02…`，只讀）。

| 類型 | 列數 | 例 |
| --- | --- | --- |
| 開頭縣市重複，去重後 `canonicalize` 可解析 | 1,231（新竹市 715、嘉義市 516） | `新竹市新竹市香山區埔前里16鄰牛埔北路37巷89弄9號` |
| 開頭縣市重複，去重後仍不能解析（區名前多一個「市」） | 8（嘉義市 6、新竹市 2） | `嘉義市嘉義市市東區…`，轉換鍵的 town 為 `市東區` |
| 其他 | 1 | `高雄市v新興區民族二路72號二十二樓之1`，轉換鍵的 town 為 `v新興區` |

原因：
- `addresses/identity.py` 的 `building_key_v2` 依 R04-6 擁有者決定，用 `_REPEATED_COUNTY` 去掉完全重複的縣市名再產生鍵。
- 地址池 `address_pool.build_pool` 先呼叫 `offline/match.py` 的 `AdministrativeNames.canonicalize`，縣市與區都找到才產生鍵。`canonicalize` 從地址開頭在行政區名稱樹上找最長相符，沒有做同樣的去重；而且建樹時刻意跳過「市名＋市名」這類名稱。所以 `新竹市新竹市…` 找不到區，回傳空縣市與空區，地址池記為 `invalid_admin`。
- 另一個現象：`building_key_v2` 不核對區名是否存在，所以 `市東區`、`v新興區` 這類錯字區名也產生了鍵。地址池因 `canonicalize` 失敗而沒有採用這些鍵，結果是保守的。

建議修法（交規劃者決定是否開卡）：
1. 在 `canonicalize` 開頭（或 `build_pool` 呼叫前）套用與 `building_key_v2` 相同的 `_REPEATED_COUNTY` 去重，兩處共用同一個規則。這會改變地址池輸出，需要重建地址池、離線狀態與之後的快照。預期 1,231 列改為可解析。
2. 8 列區名前多一個「市」，以及 1 列 `v新興區`，屬來源錯字，維持 `invalid_admin` 由人工查核。不要放寬 `canonicalize`。
3. 是否讓 `building_key_v2` 核對區名，涉及鍵規則與 `NORMALIZATION_VERSION`，需另行決定。

下一步：規劃者決定是否依上述建議 1 開卡；R05-7 產生 `district_missing`、`district_ambiguous`、`road_only_not_unique`。

## R05-4 定位採用規則

### 完成內容

- 規則放在 `lvr_pipeline/results/reconcile.py`，與產生每鍵座標摘要的 `resolve_offline` 同一處。原本該函式以 SQL 算出相異座標數，數量為 1 才定位。現在 SQL 改為把每鍵的相異座標（含來源列數與最小 `evidence_id`）列成清單，交給新函式 `adopt_coordinates` 判定。`resolution_row` 產生明細列，`haversine_m` 與 `offline/index.py` 的 `_haversine_sql` 使用同一公式及半徑 `EARTH_RADIUS_M`（6,371,008.8 m）；測試核對兩者在 DuckDB 與 Python 的結果相同。
- 判定：只有一個相異座標時與原本相同。多個相異座標時，兩兩距離的最大值不超過容許值（含等於）即為已定位，代表點取距離總和最小的來源座標；總和以 `math.fsum` 計算，避免加總順序影響同分，同分取 (經度, 緯度) 最小者。任一對超過即為衝突，不定位。不取首列，不平均。
- 容許值：`config/pipeline.example.toml` 新增 `coordinate_tolerance_m = 30.0`。`resolve_offline` 新增關鍵字參數 `coordinate_tolerance_m`，未給時讀取此設定檔；`resolve-offline` 子命令新增選用參數 `--config`。容許值、規則名稱 `pairwise_haversine_medoid` 與地球半徑寫入 `offline-state` 階段的綁定參數，也就是 `producer_config`。改容許值會改變綁定：省略 `--run-id` 時產生新快照，沿用舊 `--run-id` 時程式以 `Existing snapshot has different bindings` 拒絕。

### 偏離

- 指示寫「從 `fast2-normalize` 起重跑」，但列出的第一步是 `build-offline-index`，而 `build-address-pool` 讀的是轉換快照。本次沒有重跑 `export-converted`，直接以既有的 `fast2-converted` 作為輸入。好處是地址池與 `fast2` 相同，比較只反映定位規則。
- 卡片的修改範圍只列 `results/reconcile.py` 與設定檔。為了讓 TGOS 匯入後的狀態與離線狀態一致，另改了 `tgos.py`，並在 `contracts/`、`storage/parquet.py` 新增明細契約與驗證。

### 卡外發現

- 只有兩個相異座標時，兩點的距離總和必然相同，代表點一律依同分規則取 (經度, 緯度) 較小者，不看哪一點的來源列較多。9,112 個新定位鍵中有 6,452 鍵屬此情況，例如新樹路 448 號取了來源 1 列的點，沒取 4 列的點。這是依已核准規則的結果，未改；是否要把來源列數納入同分規則，由規劃者決定。
- 規則套用到同鍵全部有效證據，包括 TGOS 回傳。TGOS 只送查未命中鍵，實務上很少與地址基底座標同鍵；若同鍵出現兩者，30 m 內也會取中心點。TGOS 查詢層級的 `conflict` 標記（`import_tgos` 比對先前座標是否完全相同）未改。
- 地址池的 `canonical_address` 會帶樓層文字，例如「臺中市大雅區中山北路437號七樓之2」，但地址鍵不含樓層。既有行為，未改。
- `docs/architecture.md` 尚未說明 `coordinate_resolutions.parquet` 與 `--config`，本卡未修改文件。
