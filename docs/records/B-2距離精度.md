## 資料核對與資源

- `reconcile.round_distance_m` 以 `floor(x * 1000 + 0.5) / 1000` 四捨五入，不用 Python 內建 `round()`，因為它是四捨六入五成雙。`_haversine_sql` 在 SQL 用同一算式，所以 `results/review.py` 的呼叫處不必修改。
- `haversine_m` 的距離、`adopt_coordinates` 的 `math.fsum` 總和都先四捨五入，30 m 門檻與代表點都以四捨五入後的值比較。離線索引的 SQL 沒有距離總和，只有 `max(distance_m)`。
- `contracts/validate.py` 不變，仍以完全相等比對，因為儲存值與重算值走同一條四捨五入路徑。
- 邊界測試：原始距離 30.0002 m 與 30.0004 m 採用，30.0006 m 與 30.0009 m 記 `conflict`；DuckDB 與 Python 在 50 組隨機點對上相等。
- 既有測試改一處：`tests/unit/test_address_audit.py:115-117` 的距離期望值改為四捨五入後的 `111.195`。

## 結論與限制

- 程式實作完成，合成測試通過。
- 依 B 子企劃陷阱，本程式不得單獨進 run：基線的 `coordinate-resolution` 以舊精度產生，新程式讀基線會在逐列重驗時失敗。B-5 的過渡基線全量重跑才使用它。
- 跨平台相符尚未驗證，在 E 段 e02 以 Linux 容器重產驗收。
