## 起因與量測

R07-12g 後，以 run b 的全量快照直接呼叫 `write_output` 與 `verify_output` 做探測，結果在 `data/tmp/r07-10/probe/`：`write_output` 3,734 s、3,551,724 列、554 個每月 CSV，最大 91,403,400 bytes；`verify_output` 通過，228 s，66 個 50 MiB 警示；最高 RSS 2.67 GB。每月約 17.5 到 22 s，與列數幾乎無關。

`EXPLAIN ANALYZE` 量測，腳本與結果在 `data/tmp/r07-12h/profile/`：`10006` 一個月 13.9 s、`11010` 23.2 s。時間在 Parquet 掃描，例如 `components` 每次掃 174 個檔，佔 3.7 到 9.1 s 運算子時間；觀測與明細也每月重掃。join 與排序各約 1 到 3 s。

## 實作

`lvr_pipeline/output/rows.py` 的 `iter_door_rows` 先把來源物化一次到溢寫目錄內的 DuckDB 檔 `spill/rows-*/rows.duckdb`：`ob`、`ob_key`、`doors`、`d_build`、`d_land`、`d_park`，都依分區鍵 `k` 排序寫入。`doors` 是元件加上 `door_count`，視窗函數照舊算全部元件，再 join 已定位的結果。每月查詢只讀物化表的 `k = ?`，SELECT 欄、明細 `list()` 排序與 `ORDER BY` 不變。溢寫目錄由呼叫者在結束後刪除。舊實作已取代。

## 資料核對與資源

全量探測：物化一次約 175 s，之後每月中位數 8.9 s，最大 22.6 s，耗時隨列數增加，剩下主要是 Python 逐列處理。output 合計 2,215 s，改前 3,972 s。

最高 RSS 由 2.67 GB 升為 9.73 GB，推測是物化排序的緩衝，未再拆解。DuckDB 8 GiB 上限未超過。run b 的 review 階段已達 9.62 GB，所以全量 run 的最高 RSS 預期不會因此大幅改變；機器 61.6 GB。

## 結論與限制

程式實作、合成等值、2 批次逐檔相同、全量逐檔相同與全套測試完成。Windows 偶發 `PermissionError` 在本卡測試再出現一次，原因仍未查明。`verify_output` 與 `verify_relations` 的溢寫仍在系統暫存目錄。
