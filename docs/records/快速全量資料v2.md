## 結論與限制

- 結果：F-3 第一步 `normalize` 失敗。依任務卡停止規則停下回報，未修改程式，未執行後續命令。

- 估算維護包大小時，每個成員以「原始大小加 512 bytes」計，再加 4,096 bytes 的 ZIP 基本開銷。總和不超過 `max_asset_bytes` 時，維持原本的單一 `<id>_maintenance.zip`（沒有 `role` 欄位）。超過時，改為整檔分片。
- 選這個做法的原因：舊格式與既有測試（含 `test_fresh_verified_maintenance_download` 預期下載 2 個檔案）完全不變，只有真正超限的輸出才換新格式，公開的 `p2-115q1-offline-v2` 無需任何處理。代價是產出格式取決於輸入大小，讀取端必須兩種都支援（已支援）。
- 分片：成員依路徑排序後依序裝入，每片獨立 zip，命名 `<id>_maintenance.partNNN.zip`。單一檔案（加開銷）超過上限時報錯，不切割檔案。因為按原始大小保守估算，每片壓縮後必不超過上限，寫出後仍再檢查一次。
- 索引 `<id>_maintenance_index.json`：`schema_version`、`kind: maintenance-index`、分片清單（name、bytes、sha256）、成員清單（path、part、bytes、sha256）、`part_count`、`member_count`、`member_bytes`。索引登記為 `kind: maintenance`、`role: index`，分片為 `kind: maintenance`、`role: part`。
- `extract_handoff` 以副檔名 `.json` 判斷索引模式：核對索引合計值、每片存在與雜湊、每片的成員清單與索引相同、解開後檔案集合與索引完全相同、每個成員的大小與雜湊。其餘（舊單檔）沿用原路徑。
- `verify_output`：有索引時，要求索引唯一、索引分片集合等於清單中的分片資產，再走索引模式解開驗證。`distribution.fetch_output --maintenance` 在選中的資產中找 `role: index` 的資產。`scripts/verify_public_snapshot.py` 只透過 `fetch_output` 取得，不需修改。
