## 結論與限制

- 結果：F-3 第一步 `normalize` 失敗。依任務卡停止規則停下回報，未修改程式，未執行後續命令。
- 失敗原因（推測，未驗證）：驗證器要求 `expansion_status == "confirmed"` 的地址元件，其 `building_key` 必須等於 `building_key_v2(normalized_address)`，否則為 `None`。正規化產出的某些元件不符。可能與 v2.4 變更（一字區名、重複縣市去重、子門牌兩種寫法分開）有關，需要檢查是哪些地址。
- F-4 預先檢查（尚未執行）：`prepare-tgos` 不接受 `--limit 0`（程式要求 1 到 10000），而且每次執行都會建立新批次與新的 `data/tgos/` 交換資料夾，也沒有候選地址時直接報錯。因此它無法只帶入既有批次 `tgos-0358ee6e90df`。F-4 需要程式修改或擁有者另行指示。
- 快速版 v2，非驗收。

### prepare-tgos 結果

| 項目 | 數值 |
| --- | --- |
| 新批次 | `tgos-17de02009526`，狀態 `prepared`，10,000 筆 |
| 交換檔 | `data/tgos/20261008-17de0200/addresses.csv`，SHA-256 `060a886579c708cc86b4bef04a1e261fd2662329597de50145994623fb739827`，10,000 筆資料列 |
| 帶入批次 | `tgos-0358ee6e90df`，狀態 `submitted`，10,000 筆，`csv_sha256` 與 F-1 相同（`a6b3cc96…832f734`） |
| 與已送出批次的重複 | 以查詢指紋與地址鍵比對：0 個重複。以 `Address` 字串比對：124 筆相同 |

124 筆字串相同的原因：這些地址是 `…243號之28` 一類寫法。v2.4 的地址鍵把 `243之28` 與 `243號之28` 分開（R04-6b 之後的子門牌規則），所以程式認定是不同查詢而再次送出。這 124 筆會重複送 TGOS，約占 1.24%，不影響正確性，但浪費額度。任務卡的「新批次不含已送出的地址」依鍵判斷成立，依字串判斷不成立。

### import-tgos 失敗

- 停止原因：命令失敗（任務卡停下回報條件）。
- 失敗原因（推測，未驗證）：匯入後的驗證要求每個 `building_key` 在離線證據中的座標數與證據數，等於地址結果的座標數與證據數。匯入重建的狀態與 `offline_row` 證據不一致。F-1 在舊狀態（v2.0 鍵）匯入成功，這次是 v2.4 鍵的新狀態。
- 沒有統計五類結果，沒有核對別名表，沒有 `verify-tgos-state`。F-5 未執行。
