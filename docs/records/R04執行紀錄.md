- `building_key_v2("臺北市臺北市大安區和平東路二段100號")` 回傳 `town="臺北市"`、`locality_road="大安區和平東路二段"` 的鍵，不是 `None`，也與單一字首地址的鍵（`town="大安區"`、`locality_road="和平東路二段"`）不同。

- 風險：同一棟建物若一筆地址有重複字首、另一筆沒有，會被判為不同建物（不會誤併，會漏併）。

### 搬移前的候選規則（`resolve`）

`resolve` 回傳 `(tier, candidate_address, evidence)`，前置條件是路名剛好含一個亂碼字（`?` 或 PUA）。

| 候選數 | 原結果 |
| --- | --- |
| 0 | `none`，evidence `no-corpus-match` |
| 多個 | `none`，evidence `multi-match:N`；沒有取第一個，也沒有保存候選清單 |
| 1 | 補字後，若 `coord_probe(candidate_address)` 為真則 `tier1_apply`，否則 `tier2_review` |

- `address_pool.py` 只判斷 `tier == "tier1_apply"`；其他結果一律寫成 `candidate_review`、`building_key` 為空。所以多個候選原本就不會被採用，也等同待覆核。結論：不存在「多候選取第一個」的問題。

### 修改

- `resolve` 在唯一候選後新增檢查：`building_key_v2(candidate_address)` 為空（沒有門牌，或含連字號、範圍、多個「號」）時回傳 `tier2_review`，evidence `corpus_match_no_door:<路名>`，不再呼叫座標探測。有效門牌才進入原本的座標判斷。這裡的「有效門牌證據」直接沿用 `building_key_v2` 的判定，沒有新增規則；`identity.py` 未修改，只匯入。

- 限制：多候選時 evidence 仍只有數量，不含候選清單（`resolve` 的既有測試釘住 `none` 與 `multi-match` 字樣，未更動）。

2. 條文要求「規則有範圍與證據」。`塩`、`双` 沒有命中資料可證明；五條詞組規則範圍外仍有未補的亂碼列，且證據只有新舊一致。依條文，這些規則被保留、受範圍限制、未被誤用、範圍外的列仍保留亂碼可查到（有診斷），**這個論點可以支持「未驗證規則不破壞 V-05」**；但「有證據」一項對這 7 條無法由條文推出已滿足，所以不以此為通過理由。
3. 多候選只留數量：條文只要求「仍可查到」，數量加 `candidate_review` 滿足；任務卡 R04-7「保存候選清單」只對唯一候選成立。這不單獨破壞 V-05，但無法回溯是哪些候選。
