## 資料核對與資源

只用合成輸入，不涉及來源列數或磁碟用量。測試涵蓋：

- 無判定也無 TGOS 時，`final-state` 等於 offline-state，`coordinate_sources` 與受影響清單都是空的。
- 一個 `manual_coordinate` 判定：只有那個門牌所在的年月與類別 CSV 加 GeoParquet 列入清單並改變，其他 CSV 雜湊不變。`compare_catalogs` 通過。`coordinate_sources` 列數等於該鍵的觀測數，輸出地址等於判定地址。同一鍵出現在兩個年月與三個類別時，六個檔案都列入清單。
- 一個新的 TGOS 採用，來源記 `tgos`。
- `tgos_manual_conflict` 在 30 m 內保留 TGOS 座標，超過時記 `conflict`，該門牌不輸出。
- 與比較基準相比有門牌消失時階段失敗，不發布快照。
- 相同輸入重跑，檔案雜湊相同且階段重用。
- 缺區地址的人工判定經 `coordinate_sources` 給座標。
- 來自另一個 run 的比較基準可以接受；它的 converted manifest 雜湊不同（`d57adeb1…` 對 `afc53fcc…`）。產生程式不同的比較基準被拒絕，這個案例以 monkeypatch 改一個產生程式檔案雜湊造出。

## 結論與限制

已完成：程式實作與階段層級合成測試。d08 與 d12 的 `run-full` 部分等B 段，d13 已完成。尚未做：真實資料驗收（D-4）。

- 抽查時退回一次：子代理第一版要求比較基準與本次 run 的 converted 雜湊相同。回補一律使用新 run ID，而 converted manifest 會隨 run 改變，所以真實的比較基準永遠會被拒絕。修正後改為核對 `producer_files` 與 `rebuild_epoch`，並以 `transaction_id` 加 `door_index` 對應門牌。
- 只存在於比較基準、本次資料中沒有的門牌，無法偵測為消失。
- 修改 `test_second_review.py` 的一個斷言：原本對 TGOS 已定位鍵的判定記 `orphaned`，依 10-18 決定改為以 `tgos_manual_conflict` 套用。
