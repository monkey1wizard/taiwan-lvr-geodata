# 輸出欄位

修訂日期：2026-10-12，Asia/Taipei。狀態：新版公開欄位、識別契約、明細關聯契約、格式及目錄是已決定規格，尚未實作或驗收。本文件是唯一新版公開輸出契約。`data/output/` 是已決定的公開 Git 位置，但目前 `.gitignore` 仍忽略整個 `data/`。輸出流程實作、來源映射驗證及待補契約見[重建企劃](plans/重建企劃.md)。用詞見[名詞表](glossary.md)。

2026-10-12 擁有者決定重整欄位架構，由 35 欄改為 22 欄。原因是舊架構把同一個值存了多次，再以補救欄位掩蓋重複。本次同時定案 R07-6 的識別與明細關聯契約。35 欄版本原文保存在 Git 歷史，不作現行規範。

## 原則

- 輸出只有門牌圖層。一個有座標的門牌一列，幾何為 Point。不提供交易圖層。
- 照實呈現交易。原始資料只有一個總價時，就只呈現一個總價，不分攤到各門牌，也不推算各門牌的價格。
- 每個值只存一次。可以由其他欄位算出的值不設欄位。每列都相同的值不放進資料表，改記在 `catalog.json`。
- 身分使用可讀的自然鍵，可直接回查原始 CSV，不另設雜湊欄位。
- 一筆交易有多個門牌時，每一列都要讓人看出這是多門牌交易，也看得出這筆交易合併了什麼。
- 有含車位時，車位的類別、價格、面積照原始值呈現。車位數量在 `props_json` 的 `交易筆棟數` 或 `租賃筆棟數`，各車位明細在 `park_json`。
- 只收錄有座標的門牌。沒有座標的門牌等 TGOS，不放進輸出。
- `address` 是這個點代表的門牌。`transaction_addresses` 是地址欄原文。TGOS 更新 `address` 的前提是依新規則核驗該回傳，並明確納入本次新基線。
- 本次新基線中經新規則核驗並納入的 TGOS 或人工查核結果，可更新覆蓋地址與座標結果。不得自動讀取重建前的 TGOS 採用結果、review 裁定或舊快照。座標由誰決定不放進輸出，記在執行目錄，見「記在執行目錄，不放進輸出」。
- 不使用 decimal 型別，因為 GeoPackage 不支援。原始資料的金額全為整數，存成 int64。面積帶小數，存成 double。
- `props_json` 保留，內含主檔該列的全部原始欄位。
- 22 個欄位及下方檔案映射是已決定的欄位範圍。新輸出模組已能產生，但尚未接入 `run-full`，也尚未驗收。

## 一筆交易多個門牌時

例：原始地址欄 `臺北市萬華區中華路二段３８、３８之１、３８之２、３８之３號`，總價 3,250,000 元，4 個門牌都有座標。輸出有 4 列：

| 欄位 | 第 1 列 | 第 2 列 | 第 3 列 | 第 4 列 |
| --- | --- | --- | --- | --- |
| `transaction_id` | 同一個值 | 同一個值 | 同一個值 | 同一個值 |
| `door_index` / `door_count` | 1 / 4 | 2 / 4 | 3 / 4 | 4 / 4 |
| `address` | 中華路二段３８號的門牌文字 | ３８之１號的門牌文字 | ３８之２號的門牌文字 | ３８之３號的門牌文字 |
| `transaction_addresses` | 地址欄原文 | 地址欄原文 | 地址欄原文 | 地址欄原文 |
| `price_twd` | 3,250,000 | 3,250,000 | 3,250,000 | 3,250,000 |

只有 2 個門牌有座標時，輸出只有那 2 列，`door_count` 仍是 4。其中某個門牌經 TGOS 更新後，該列的 `address` 改為 TGOS 的結果。

使用者從任何一列可以知道：

- 這是多門牌交易：`door_count` 大於 1。
- 合併了哪些門牌：`transaction_addresses` 是地址欄原文。
- 合併了哪些標的：`transaction_target`、`props_json` 中的筆棟數，以及 `land_json`、`build_json`、`park_json`。
- 總價、單價屬於整筆交易，不是這一個門牌：`price_twd`、`unit_price_sqm` 在各列相同。加總時依 `transaction_id` 去重。
- 同一筆交易的其他點：以 `transaction_id` 篩選。
- 還有幾個門牌在等 TGOS：`door_count` 減輸出中同一 `transaction_id` 的列數。

## 識別契約

本節是 R07-6 定案的身分規則。

### `transaction_id`

- 格式為 `{src_batch}/{member_path}/{source_row_number}`，例如 `115q1/a_lvr_land_a.csv/6076`。三段以 `/` 分隔。
- `src_batch` 是來源 ZIP 的批次標籤，格式 `[0-9]{3}q[1-4]`。`member_path` 是 ZIP 內主檔檔名。`source_row_number` 是該列在主檔中的實體行號，從 1 起算，標題列是第 1 行，第二行英文標題計入行號。
- 程式必須檢查 `member_path` 不含 `/`，批次標籤符合格式，行號為正整數。任一項不符即為失敗列，不產生 id。
- 一個輸出版本內，每個批次只有一個 ZIP，其 SHA-256 記在 `catalog.json`。id 加上 catalog 的批次雜湊才構成完整來源身分。
- id 只在同一個輸出版本內有效。內政部重新發布同一批次時，相同位置的列會得到相同 id，但不代表是同一筆交易。跨版本比對必須先核對 `catalog.json` 的批次雜湊，雜湊不同時不得假設 id 相同即交易相同。
- 內部 `raw_record_id` 仍是三項輸入的 SHA-256，用於快照與證據綁定。兩者由相同輸入算出，一對一對應。公開輸出不含 `raw_record_id`。

### `door_index` 與主鍵

- `door_index` 是地址欄拆解後的門牌順序，從 1 起算，依原文出現順序。內部 `component_id` 的序號從 0 起算，`door_index` 等於內部序號加 1。
- 主鍵是 `transaction_id` 加 `door_index`。不另設單欄主鍵。
- 門牌拆解規則版本記在 `catalog.json`。規則版本改變時，同一交易的拆解結果與 `door_index` 可能改變。契約不保證 `door_index` 跨規則版本穩定。
- 執行目錄中記錄 TGOS 或人工查核更新的門牌時，以 `transaction_id` 與 `door_index` 兩欄對應。

### 各格式的主鍵呈現

| 格式 | 呈現 |
| --- | --- |
| GeoParquet | 兩欄。依 `trade_date`、`category`、`transaction_id`、`door_index` 排序 |
| GeoPackage | 兩欄。`fid` 由 GeoPackage 自行產生，不是契約的一部分，重產時可能不同 |
| GeoJSON | Feature `id` 在寫檔時由 `{transaction_id}#{door_index}` 組成，不另設屬性欄 |
| CSV | 兩欄 |

## 欄位

同一筆交易的各列，除了 `door_index`、`address` 與座標，其他值都相同。

### 身分與地址

| # | 欄位 | 型別 | 說明 |
| --- | --- | --- | --- |
| 1 | `transaction_id` | string | 交易識別碼，見識別契約 |
| 2 | `door_index` | int64 | 這是該交易拆出的第幾個門牌，從 1 起算。與 `transaction_id` 合為主鍵 |
| 3 | `door_count` | int64 | 地址欄共拆出幾個門牌。大於 1 就是多門牌交易 |
| 4 | `address` | string | 這個點代表的門牌，是地址欄拆解後的單一門牌文字。單門牌交易時與原文相同。TGOS 有更新時改為 TGOS 的結果 |
| 5 | `transaction_addresses` | string | 地址欄原文，可能含多個門牌與樓層 |

### 交易內容

| # | 欄位 | 型別 | 說明 |
| --- | --- | --- | --- |
| 6 | `category` | string | `sales` 買賣、`presale` 預售屋、`rent` 租賃 |
| 7 | `trade_date` | string | 交易日期，西元 YYYY-MM-DD |
| 8 | `county` | string | 縣市 |
| 9 | `district` | string | 鄉鎮市區 |
| 10 | `transaction_target` | string | 交易標的原文，例如 `房地(土地+建物)+車位` |
| 11 | `building_type` | string | 建物型態 |

### 金額與面積

三欄都是整筆交易的原始值，不是這一個門牌的值。

| # | 欄位 | 型別 | 說明 |
| --- | --- | --- | --- |
| 12 | `price_twd` | int64 | 整筆交易的總價，元。租賃為總額。含土地、建物、車位 |
| 13 | `unit_price_sqm` | int64 | 每平方公尺單價，元，原始值。原始資料可能為空 |
| 14 | `area_m2_decimal` | double | 建物面積，平方公尺。買賣、預售為建物移轉總面積，租賃為建物總面積 |
| 15 | `parking_type` | string | 車位類別原文。沒有車位時為空 |
| 16 | `parking_price_twd` | int64 | 車位總價，元，原始值。0 表示原始資料未分開計價 |
| 17 | `parking_area_m2` | double | 車位面積，平方公尺，原始值 |

### 座標

| # | 欄位 | 型別 | 說明 |
| --- | --- | --- | --- |
| 18 | `geometry` | geometry | Point，WGS84。GeoParquet、GeoPackage、GeoJSON 使用。CSV 改為 `longitude`、`latitude` 兩欄 double |

### 原文與明細

| # | 欄位 | 型別 | 說明 |
| --- | --- | --- | --- |
| 19 | `props_json` | string | 主檔該列全部原始欄位，JSON 物件，鍵名為原始欄位名 |
| 20 | `build_json` | string | 該交易全部建物明細，來自 `_build.csv`，JSON 陣列 |
| 21 | `land_json` | string | 該交易全部土地明細，來自 `_land.csv`，JSON 陣列 |
| 22 | `park_json` | string | 該交易全部車位明細，來自 `_park.csv`，JSON 陣列。每個車位各自的價格與樓層在這裡 |

GIS 格式共 21 個屬性欄加 1 個幾何欄，合計 22 欄。CSV 沒有 `geometry`，在同一位置改為 `longitude`、`latitude`，合計 23 欄。GeoPackage 另有自身的 `fid`，不屬契約欄位。

## 明細關聯契約

本節是 R07-6 定案的明細規則。

### 檔案與關聯鍵

- 主檔 `{縣市字母}_lvr_land_{類別}.csv` 的明細檔是同一 ZIP 內的 `{縣市字母}_lvr_land_{類別}_build.csv`、`_land.csv`、`_park.csv`。明細只在同一 ZIP、同一縣市字母、同一類別的檔案組內關聯，不跨批次、不跨縣市、不跨類別。
- 關聯鍵是主檔與明細檔的原始欄位 `編號`，比對前只去除首尾空白，不做其他正規化。
- 一筆交易可能對應零列或多列明細。三欄都是 JSON 陣列，一個元素是明細檔的一列，鍵名為原始欄位名，值為原始字串。元素順序依明細檔的實體行號。沒有明細時為空陣列 `[]`。多門牌交易的各列存同一份明細。
- 明細檔的欄位名，以該檔案自己的標題列為準，不假設全部批次相同。各明細成員的標題列記錄在 ingest 報告的 `detail_members`。

### 檢查與例外

程式在建置時逐檔檔案組檢查，結果寫入 run report，作為 V-10b 的證據。不先用人工掃描代替。

| 情況 | 處理 |
| --- | --- |
| 主檔某列 `編號` 為空 | 該交易三個明細欄為 `[]`。計入 run report 的 `serial_missing` |
| 主檔同一檔案內 `編號` 重複 | 這些交易的三個明細欄為 `[]`，不掛任何明細，避免掛錯。計入 `serial_duplicated` |
| 明細檔某列 `編號` 在主檔找不到 | 該明細列不輸出。計入 `detail_unmatched` |
| 明細檔某列 `編號` 對應到主檔的重複編號 | 該明細列不輸出。計入 `detail_ambiguous` |
| 明細檔不存在 | 該檔案組對應的明細欄為 `[]`。計入 `detail_member_missing`。不把缺檔視為沒有明細 |
| 明細檔標題列缺 `編號` | 整個明細檔不關聯，同上處理。計入 `detail_serial_column_missing` |
| 明細列欄數與標題不符 | 該明細列不輸出。計入 `detail_row_failed` |

每個計數都按批次、檔案組與明細種類分列。任一計數大於 0 不阻止輸出，但必須出現在 run report 與驗收紀錄。

## 公開目錄、公告與維護資料

新版目標目錄固定為 `data/output/`。目錄表及檔案分工如下，這是已決定目標，尚未由程式實作：

```text
data/output/
├── NOTICE.json
├── catalog.json
├── gpkg/taiwanlvr_YYYY.gpkg
├── csv/YYYY/taiwanlvr_YYYY_<類別>.csv
├── csv/YYYY/taiwanlvr_YYYYMM_<類別>.csv
└── geojson/YYYY/taiwanlvr_YYYYMM_<類別>.geojson
```

GeoParquet 為完整資料單檔 `taiwanlvr.parquet`，依交易日期及類別排序，放在 GitHub release，不放入 `data/output/` Git 目錄。GeoPackage 每年一檔，含買賣、預售屋、租賃三圖層；CSV 有每年及每月、每類別檔案；GeoJSON 每月、每類別一檔。目錄及檔名中的月份使用兩位數。

`catalog.json` 是此公開目錄的檔案索引。每個資料檔案須列出格式、適用的年、月與類別、期間粒度、筆數、檔案大小、SHA-256 及檔案位置。期間粒度區分全歷史、整年及單月，檔案位置區分公開目錄的相對路徑與 GeoParquet 的 release 位置。幣別固定為 `TWD`。欄位版本、拆解規則版本與截止年月等本次輸出共通資訊記於 catalog，不重複放進每列。JSON 的具體序列化與欄位版本命名仍待實作契約補足。

`config/sources/notice.json` 是正式公告的唯一來源，產出時複製為 `data/output/NOTICE.json`，取代舊版公告。檔案目前不存在。公告中的實際來源範圍、來源顯名與限制尚待確認，不從其他公告或本文件推定。

維護資料只存在本機 `data/runs/<run-id>/maintenance/`，不得放進公開目錄或 release。只有本次全新重建且通過 V-10b 的基線所產生、可追溯綁定該基線的維護包，才可供 R08-2a 無原始 ZIP 重產候選及後續私有維護；重建前維護包與舊衍生產物一律禁止。維護包本身不代表候選已通過公開驗證。TGOS 狀態目標位置為 `data/runs/<run-id>/tgos-state/`；第二類人工查核區在 `data/runs/<run-id>/review/`，與待查核表及交叉比對清單分開。以上皆為已決定目標布局，現行命令／預設路徑及 `data/` ignore 尚待實作調整。

- GeoParquet 依交易日期與類別排序。
- GeoJSON 的 Feature `id` 為 `{transaction_id}#{door_index}`。
- CSV 為 UTF-8，是否加 BOM 待實測 Excel 後決定。
- GeoPackage 內嵌 QGIS 預設樣式（2026-10-12 擁有者決定）：`door_count > 1` 的點以不同符號顯示，點旁標示 `door_index/door_count`。QGIS 開啟圖層時自動套用。
- CSV 與 GeoJSON 不能內嵌樣式。依 `door_count` 著色、依 `transaction_id` 篩選同一筆交易的方法，寫在 README。

## 加總金額的規則

依 `transaction_id` 去重後再加總 `price_twd`。直接加總全部列，多門牌交易的金額會重複計入。`unit_price_sqm` 同樣是交易層的值，不是各門牌的單價。

## 單價的觀察

歷史觀察：依舊版 115q1 臺北市資料比對，車位有另外計價時，多數單價符合「(總價 − 車位總價) ÷ (建物面積 − 車位面積)」。車位沒有另外計價時，多數符合「總價 ÷ 建物面積」。這是當時的比對結果，不是內政部的官方說明，也不是本次新重建驗收證據。輸出照原始單價呈現，不重算。

### 三、舊版對照觀察（非新驗收事實）

以下內容是舊版 58 批來源盤點及其對照結果。保留原觀察供追查，不代表本次選定來源的涵蓋、欄位或資料正確，也不能替代獨立重核。

1. 程式為預售準備的別名 `交易年月`、`房地總價元`，以及為租賃準備的 `月租金`，在 58 批中都沒有出現。
2. 總價、總額、單價、車位價格在 58 批中全為整數。建物面積全部帶小數，建物移轉總面積最多 18 位、建物總面積最多 15 位小數，多數應為浮點殘留，此為推論。其他面積最多 2 位小數。
3. `車位移轉總面積平方公尺` 在較舊的 473 個買賣 CSV 寫成 `車位移轉總面積(平方公尺)`。兩者只出現在 `props_json`，鍵名依批次不同。
4. `county` 由檔名判斷，`district` 取自 `鄉鎮市區`，兩者都是交易層的值。一筆交易的多個門牌如果分屬不同行政區，每一列仍顯示同一個縣市與行政區。
