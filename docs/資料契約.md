# 內部資料契約

本文件說明來源觀測、地址成員、地址鍵、定位證據、狀態及快照間的內部關聯。它不定義公開欄位。公開輸出規格唯一見[輸出欄位](輸出欄位.md)。階段輸入與產物見[資料處理流程](資料處理流程.md)。

## 2026-10-12 重建與信任邊界

本次決定中的「既有」與「舊結果」指全新重建開始前已存在的處理產物。本次重建完成獨立驗收後，新產生的維護包及結果可依企劃供 R08 候選重產與 R10 回補使用，不能藉此納入重建前的產物。

既有衍生結果全部不可信，不作新流程輸入、定位依據或新版驗收基準。範圍包括 normalized／converted、地址池／index／state、aliases、TGOS 採用結果、review 裁定、衍生 cache、快照、維護包、公開輸出及統計。歷史 raw ZIP 與地址來源保留追查，但不能因曾輸入舊流程或通過舊驗收而視為已核驗或自動沿用。新 run 須重建來源清冊並重新核對原文和來源涵蓋。舊 TGOS 回傳結果已於 2026-10-13 由擁有者決定廢棄，不重核、不納入任何新結果；本機已無這些檔案。

舊 TGOS 帳本與舊回傳在本機已不存在，不轉接、不擋重送；新重建以新帳本從零開始，離線定位不到的門牌全部重新送查。 新帳本在重建期間不可清空或繞過。新 run 的快照限於本次重建中已依新規則驗證、且輸入綁定相同的階段。隔離護欄已於 2026-10-12 實作（R07-6a）：沒有 `rebuild_epoch = 2026-10-12` 的快照與 run 一律拒絕讀入，規則版本不符的快照也拒絕；`run-full` 只接受帶本次紀元的來源清冊與地址來源描述；2026-10-13 決定取消人工簽核，R07-6c 已移除 `source_check` 檢查，清冊改記 `scanned_at`。依 2026-10-17 決定保留同紀元帳本帶入 `--ledger`；R09-2 已刪除為舊帳本加的無鍵查詢處理，帳本中有無鍵查詢時拒絕。

## 資料單位與關聯

```text
來源檔案列
  └── 來源觀測 raw_record_id
        └── 一個或多個地址成員 component_id
              └── 地址鍵 building_key
                    └── 零個或多個定位證據
                          └── 定位狀態與採用結果
```

| 單位 | 識別及含義 | 關聯原則 |
| --- | --- | --- |
| 交易 | 原始來源主檔一列 | 不跨批次合併，不依相同地址或原始流水號推斷多列相同 |
| 來源觀測 | `raw_record_id` 由來源 ZIP 雜湊、ZIP 內成員路徑及實體列號識別主檔列 | 保留每個來源列及其去向。不推斷修訂先後 |
| 地址成員 | `component_id` 由來源觀測及地址拆解序號識別一個門牌成員，內部序號從 0 起 | 一筆觀測可有多個成員。地址欄原文及拆解順序要保留 |
| 地址鍵 | 目標介面 `building_key` 依現行 v2 地址規則識別門牌；規則版本放入 metadata | 多個觀測成員可指向同鍵。只共用本次重建定位結果，不合併觀測 |
| 定位證據 | `evidence_id` 及來源參照指向一筆地址或座標依據 | 保留候選、來源、輸入版本、座標與採用或拒絕原因 |
| 定位狀態 | 以地址鍵表示目前可用的定位結論 | `located`、`unmatched`、`conflict` 及 `outside_scope` 是不同結果，不可互換 |

公開 `transaction_id` 於 2026-10-12 由 R07-6 定案為可讀自然鍵 `{src_batch}/{member_path}/{source_row_number}`。它與內部 `raw_record_id` 由相同三項輸入算出，一對一對應。批次 ZIP 的 SHA-256 記在 `catalog.json`，id 加批次雜湊才是完整來源身分。公開主鍵是 `transaction_id` 加 `door_index`，不另設 `door_id`。公開 `door_index` 從 1 起算，等於內部 `component_id` 的 0 起算序號加 1。完整規則見[輸出欄位](輸出欄位.md)的識別契約。

## 來源觀測及去向

交易主檔一列是來源觀測。正規化後，每列有且只有一個主要去向：保留、排除或解析失敗。排除原因及解析錯誤屬診斷資訊，不替代主要去向。每個來源 ZIP 成員的輸入列數必須等於三種去向總和。

內部金額 `amount_minor` 以新臺幣分儲存，比例為 100。同一來源觀測的金額不可因拆成多個地址成員而重複計算。面積以平方公尺十進位文字保留；數值 `0` 與缺值 `null` 必須區別。這些是內部契約，不能與公開欄位的整數元及 double 面積型別混為一談。

類別由來源檔名標記：`sales` 為買賣、`presale` 為預售屋、`rent` 為租賃。批次季別不等於交易年月。日期須由 `validated_roc_to_tx_yyyymm` 驗證並轉換，不能直接截取字串推定。常見排除原因包括土地、無門牌地址、純車位及無效日期，各自保留原因。來源描述標為空批次時須有證據，檔案缺失不可視為空資料。

建物 `_build.csv`、土地 `_land.csv`、車位 `_park.csv` 是分列明細。程式已讀入（R07-7）：明細列以自己的 `detail_record_id` 保留來源觀測，連結結果為 `detail` 資料集，以 `raw_record_id` 對應主檔，含被排除的主檔列。關聯鍵、檔案組範圍與七種例外的處理於 2026-10-12 由 R07-6 定案，見[輸出欄位](輸出欄位.md)的明細關聯契約。明細只在同一 ZIP、同一縣市字母、同一類別的檔案組內以 `編號` 關聯。`編號` 是否存在且唯一由建置時逐檔檢查判定並寫入 run report，不先假設。不可僅依主檔地址文字或相同編號推斷跨來源交易相同。

## 地址成員與門牌鍵

地址成員保留來源觀測識別、地址欄原文、拆解結果、順序及規則版本。無法拆出完整門牌的成員仍留在診斷與待查核資料，不從觀測關聯中刪除。

`building_key` 是唯一目標門牌鍵名稱，用於跨觀測關聯本次重建中的同一門牌定位結果。鍵內容與正規化細節以[地址規則](地址規則.md)為準。`building_key_v2` 函式與 `legacy_building_key` 欄位已於 2026-10-12 移除，不得重新加入 alias、wrapper、雙軌或舊結果 fallback。樓層不是門牌鍵的一部分。未證明身分相同的主號、子號、村里、鄰或門牌文字變體不得合併。

地址鍵不是來源觀測 ID、明細列 ID 或公開交易 ID。地址鍵重用不允許去重觀測，也不代表來源有完整歷史涵蓋。

## 定位證據與狀態

定位決策以地址鍵為單位，觀測到地址成員的關聯保留原樣。證據至少須能追溯來源版本、原始識別、地址比較結果、候選座標及規則版本。沒有被採用的候選也要保留拒絕原因。座標需明確坐標參考系及軸向，軸向未確認時不得採用。

| 狀態 | 用途 |
| --- | --- |
| `located` | 有通過同址與座標驗證的可用座標 |
| `unmatched` | 固定地址來源中沒有符合候選 |
| `conflict` | 候選身分或座標相互矛盾，未採用定位 |
| `outside_scope` | 來源地址或查詢不在本輪固定範圍。澎湖及金門暫停定位使用 `conflict` 加 `address_source_suspended`，不能記為 `outside_scope` |

同一來源地址的不同座標、同一門牌多筆候選及多門牌歧義必須分開處理。30 m 容許值只適用於同一已確認門牌內的座標差異。定位證據不證明歷史建物在所有交易時間都位於同一位置。

TGOS 帳本保存查詢原文、批次、回傳雜湊、送出狀態及匯入結果。查詢以 `query_kind` 區分門牌鍵查詢與缺區查詢；缺區查詢沒有門牌鍵，以 `digest(["district_missing", 縣市碼, 地址])` 識別並保存候選區，採用結果記回傳門牌鍵（R09-6）。相同批次和相同回傳雜湊重匯具冪等性；已完成批次以不同回傳雜湊重匯時拒絕（R09-3）。查詢名額以門牌計：門牌一經送出或狀態為 `submission_unknown` 就不再被選，不記錄每日用量（2026-10-17）。查詢與回傳需集合一對一。`submission_unknown` 保留原狀態，不能自動釋放名額或重新送出。

批次送出生命週期狀態包括 `prepared`、`submitted`、`submission_unknown`、`cancelled`。回傳匯入後狀態為 `completed`。查無或拒絕是回傳列結果，不是可替代批次送出狀態的值。每個交換檔最多 10,000 筆，這是單檔上限，不是每日程式限制。`data/tgos/date.json` 的日期只決定交換資料夾名稱，不參與候選、批次識別、送出狀態或匯入判定。

地址補充 CSV 的 14 欄名稱、順序及映射唯一見[地址規則](地址規則.md)。內部資料須保留來源關聯、採用依據及隔離原因。產生候選不代表地址專案已匯入。

## 第二類人工查核區

2026-10-17 定契約，實作歸 R10-1，施做規格見 [04 人工查核與回補](plans/04-人工查核與回補.md)。第二類人工查核區是 TGOS 之後仍沒有可採用座標、需要擁有者逐筆判定的門牌集合。它只收判定對象與判定結果，不改寫帳本、待查核表或交叉比對清單。本節不改變地址規則：村里異體字或改名不自行映射，鄰仍是子識別，`conflict` 不送 TGOS，`submission_unknown` 不重送。

### 判定單位與位置

判定單位稱為查核鍵 `review_key`。有門牌鍵時，查核鍵就是 `building_key`。缺區地址沒有門牌鍵，查核鍵是缺區查詢的 `query_fingerprint`，公式同 R09-6，未送出的缺區地址也用同一公式算出。`review_id` 為 `digest(["second_review", review_key])`。同一查核鍵在一個 run 內只有一列。

| 檔案 | 位置 | 寫入者 |
| --- | --- | --- |
| `second_review.parquet` 與同名 CSV | run 目錄 `review/` 階段快照 | 程式，每次建 review 階段重算 |
| `second_review_observations.parquet` | 同上 | 程式，一個查核鍵對多個 `transaction_id` 加 `door_index` |
| `coordinate_sources.parquet` | 同上 | 程式，記錄經 TGOS 或人工判定更新的門牌 |
| 擁有者判定檔 `YYYYMMDD-NN-<sha8>.csv` | `data/review-decisions/`，不進 Git | 擁有者，寫入後不修改 |

判定檔放在 run 目錄之外，因為判定要跨 run 沿用，例如 R09-9 全量重跑後仍有效。判定檔是擁有者證據，不屬於 2026-10-12 隔離的衍生資料。每次建置都在本次 run 依現行規則重新核對判定，核對不過的判定不套用。判定檔目錄的雜湊清單寫入 review 階段綁定與 run report。

### 進入條件

進入時機：門牌在本次 run 已沒有等待中的 TGOS 查詢，而且狀態不是 `located`。查詢狀態為 `prepared`、`submitted` 或 `submission_unknown` 時不進入，仍等回傳。從未送查的 `unmatched` 門牌也不進入，等下一輪 TGOS。

| 進入原因 `entry_reason` | 條件 | TGOS 證據 |
| --- | --- | --- |
| `tgos_not_found` | 回傳列 `status = failed`、`reason` 空白，即 TGOS 查無 | 有回傳列，無座標 |
| `tgos_isolated` | 回傳門牌與查詢不同，`mismatch_fields` 記不同的鍵欄位 | 有，含回傳地址與座標 |
| `tgos_isolated` 加 `mismatch_fields` 只含 `village` 或 `neighborhood` | 只差村里或鄰。子原因以 `mismatch_fields` 區分，不另立進入原因 | 有 |
| `tgos_coordinate_invalid` | 座標超界、只有一半或非數字 | 有，保留原值 |
| `tgos_response_incomplete` | 回傳地址不完整或成功列缺回傳地址 | 有 |
| `tgos_village_ambiguous` | 回傳村里或鄰在地址池中有兩個以上不同值 | 有 |
| `tgos_key_text_not_round_trip` | 門牌鍵重組文字算不回原鍵，未送查 | 無 |
| `district_no_candidate_town` | 缺區地址在離線索引找不到候選區，未送查 | 無 |
| `conflict` | 離線狀態為 `conflict`，不送 TGOS。暫停縣市的 `address_source_suspended` 不進入 | 無，引用交叉比對清單 |

`tgos_not_found`、`tgos_key_text_not_round_trip`、`district_no_candidate_town` 是新的進入原因。目前查無只是回傳列狀態，後兩者只是報告計數，R10-1 要把它們加入代碼表。同一查核鍵有多筆回傳時，取帳本中最新匯入的回傳作為證據，較早的回傳以 `result_id` 清單保留。

### 欄位

| 欄位 | 說明 |
| --- | --- |
| `review_id`、`review_key`、`key_kind` | 識別。`key_kind` 為 `building_key` 或 `district_query` |
| `building_key`、`query_fingerprint` | 依 `key_kind` 擇一或兩者皆有 |
| `county_code`、`town`、`canonical_address` | 本次 run 地址池的代表地址 |
| `entry_reason`、`mismatch_fields` | 進入原因與不同的鍵欄位 |
| `offline_status` | 本次 run 離線狀態 `unmatched` 或 `conflict`，缺區地址為空 |
| `tgos_batch_id`、`tgos_result_id`、`prior_result_ids` | TGOS 證據來源 |
| `response_address`、`response_building_key`、`response_lng`、`response_lat`、`response_sha256` | 回傳原值。`response_building_key` 由建置時以現行規則從回傳地址重算，算不出時為空並記原因 |
| `status`、`decision_file`、`decision_file_sha256`、`decision_row`、`decided_at` | 判定狀態與依據 |
| `observation_count`、`tx_yyyymm_min`、`tx_yyyymm_max` | 來源觀測關聯摘要，明細在 `second_review_observations.parquet` |

`second_review_observations.parquet` 每列為 `review_id`、`transaction_id`、`door_index`、`raw_record_id`、`component_id`、`category`、`tx_yyyymm`。關聯由本次 run 的地址成員算出，不合併觀測。R09-7 第 1 批的 3,640 筆地址不符列在帳本中 `response_building_key` 全部為空，所以建置時一律重算，不讀帳本該欄。

### 狀態與轉換

| 狀態 | 意義 | 誰設定、何時 |
| --- | --- | --- |
| `pending` | 待判定，預設值 | 程式在建 review 階段時設定 |
| `adopted` | 擁有者確認一個座標可代表這個門牌 | 擁有者寫判定檔，下次建 review 階段時套用 |
| `rejected` | 擁有者確認沒有可用座標 | 同上 |
| `deferred` | 延後，等新證據或下一輪 TGOS | 同上 |

轉換規則：

1. 程式只能建立 `pending`，不能自行設成其他三種狀態。
2. `pending`、`deferred` 可轉為 `adopted`、`rejected`、`deferred`。`adopted`、`rejected` 只能由擁有者的新判定改變，新判定取代舊判定，舊判定保留在判定歷程。
3. 之後的 TGOS 輪次或離線定位使門牌變成 `located` 時，該查核鍵不再進入第二類人工查核區，判定歷程保留。若門牌已有 `adopted` 判定，TGOS 採用與人工判定的先後由擁有者決定，見 R10 執行企劃待釐清事項。
4. `rejected` 的門牌不進入新 TGOS 輪次的自動候選。`deferred` 與 `pending` 可以進入，但仍受查詢名額規則限制。

### 擁有者判定檔

UTF-8、不加 BOM 的 CSV，欄位與順序固定：

```text
review_key,decision,mode,tgos_result_id,lng,lat,address,basis,decided_by,decided_at
```

- `decision` 為 `adopted`、`rejected` 或 `deferred`。
- `adopted` 必填 `mode`。`accept_tgos_response` 表示採用該查核鍵的 TGOS 回傳，`tgos_result_id` 必須等於本次帳本中該查核鍵的回傳。`manual_coordinate` 表示擁有者提供座標，必填 `lng`、`lat` 與 `address`。座標依[地址規則](地址規則.md)為 WGS84 經度、緯度，並通過有效範圍檢查。
- `basis` 必填，寫判定依據，例如「行政區表證明村改里」。`decided_by`、`decided_at` 必填，日期為 Asia/Taipei 的 `YYYY-MM-DD`。

冪等與核對規則：

1. 檔名的 `<sha8>` 是檔案內容 SHA-256 的前 8 個十六進位字元。檔名與內容不符時拒絕整個 review 階段，因為這表示判定檔在寫入後被修改。要更正判定，另寫新檔。
2. 判定檔依檔名順序套用，同一查核鍵的較晚判定取代較早判定。同一組判定檔重複套用，結果不變。
3. 同一檔內同一查核鍵出現兩次時，拒絕整個檔。
4. 查核鍵不在本次 run 的第二類人工查核區時，判定記為 `orphaned`，不套用。`tgos_result_id` 不在本次帳本或座標無效時記為 `stale`，不套用。兩者都寫入 run report 計數。
5. 判定只決定座標與代表地址，不改 `building_key`、不合併門牌鍵、不改交易原文。

### 與其他清單的分工

| 清單 | 單位 | 內容 | 誰改 |
| --- | --- | --- | --- |
| TGOS 帳本 `tgos-state` | 查詢 | 查詢原文、批次、送出狀態、回傳與匯入結果 | 只有 TGOS 命令，判定檔不改帳本 |
| 待查核表 `exception_addresses` | 觀測地址 | 所有診斷與未定位原因 | 程式，診斷用，不收判定 |
| 交叉比對清單 `cross_check_addresses` | 候選門牌 | 多門牌、多座標歧義明細 | 程式，診斷用，不收判定 |
| 第二類人工查核區 `second_review` | 查核鍵 | TGOS 後仍無座標的判定對象與判定狀態 | 程式建列，擁有者以判定檔決定 |

第二類人工查核區只以 `entry_reason` 引用其他清單，不複製它們的列。`adopted` 判定經套用後寫入 `coordinate_sources.parquet`，以 `transaction_id` 加 `door_index` 對應，記錄更新前後的 `address` 與座標及來源 `tgos` 或 `manual`。座標由誰決定不進公開輸出，見[輸出欄位](輸出欄位.md)「記在執行目錄，不放進輸出」。

## 快照、版本及續跑

每次新 run 固定本次獨立重核的來源清單、原始輸入雜湊、地址來源、地址規則版本 metadata、程式版本、契約版本及截止年月。不得使用過去 run 的衍生快照；只可在本次新 run 內重用已驗證且輸入綁定一致的階段。綁定改變時建立新結果，不覆寫原始證據。

目前 `run-full` 已具來源核對、階段快照、續跑、離線處理及 run report。R07-6a 護欄要求快照綁定與 run 綁定都含 `rebuild_epoch`，並在寫入前檢查來源清冊的紀元，不需人工簽核欄位。程式尚未將 TGOS 狀態接入 `run-full`，由 R09-8 實作。R09-2 起 TGOS 命令與 `build-review` 必填 `--run-id`，狀態寫入 `data/runs/<run-id>/`，並拒絕 `run-full` 的 run 目錄；其他 CLI 命令仍可能使用 `data/work/`。

地址來源分兩個時點檢查（2026-10-15 擁有者決定，R07-12a 實作）。釘選時，`pin-address-source` 要求工作區乾淨，且描述檔的 commit 等於地址專案 HEAD。執行時，`check_pinned_source` 要求工作區乾淨，並逐檔核對路名檔、行政區表、`road.csv` 與 `char_fixes.csv` 的大小與 SHA-256 等於 `address_source.json`；HEAD 與釘選 commit 不同時仍通過，但要記錄實際 HEAD。`source_metadata` 隨平台換行，不核對。`run-full` 在每個階段入口、續跑判斷之前執行這項檢查。同一 run 第一次做全量雜湊；之後 HEAD 不變時只核對 HEAD 與工作區乾淨，HEAD 改變就重新全量核對。每次結果寫入 run report 的 `address_source_head`。檢查失敗時記 `address_source_changed`，不建置也不提交該階段。`build_index` 與 `build_pool` 在建置前後也用同一個函式核對。

快照驗證次數（2026-10-15，R07-12b 實作）：每個檔案在 `SnapshotStore.add` 加入時逐列驗證一次，包括 JSON 欄、jsonschema、觀測 ID、日期規則與已確認元件的 `building_key`。`publish` 不再逐列重驗 Parquet，只核對結構、每檔大小與 SHA-256，再做一次跨檔關聯驗證；JSONL 列會讀回供關聯驗證。改名後與提交、`load_snapshot`、續跑判斷、`current` 都只核對結構與每檔大小、SHA-256，`RunStore.reusable` 另核對 `checkpoints.json` 的 manifest 雜湊。`verify-snapshot --path <快照目錄>` 執行完整重驗，含逐列與關聯，供稽核與 R08-2a 使用。

執行或階段驗證失敗時，保留失敗狀態與必要診斷在 `data/tmp/<purpose>/`。失敗或尚未完成的快照不進入可重用階段清單。公開輸出目錄契約見[輸出欄位](輸出欄位.md)。

## 私有維護包

2026-10-16 擁有者核准，R08-2a 實作。維護包讓沒有原始 ZIP 的環境也能重產公開候選並核對雜湊，只存本機 `data/runs/<run-id>/maintenance/`，不進 Git、release 或 `data/output/`。只能從通過 V-10b 的基線 run 匯出，目前為 `r07-10-20261016b`。

輸出階段只讀 converted 與 offline-state 兩個快照、converted 的 `quality.json` 與截止年月，`output_id` 由兩者的 manifest 雜湊算出，所以維護包只放這兩個快照。ingested 與 normalized 需要原始 ZIP 才能重建，不在維護包內。

| 路徑 | 內容 |
| --- | --- |
| `snapshots/converted/<snapshot_id>/`、`snapshots/offline-state/<snapshot_id>/` | 基線快照的原樣複本 |
| `run/manifest.json`、`run/checkpoints.json`、`run/run_report.json` | 基線 run 的綁定、檢查點與報告複本 |
| `package.json` | `schema_version`、`created_at`；`run_id` 與 `rebuild_epoch`；基線快照綁定的 `config_sha256` 與 `code_commit`；`baseline` 記 converted、offline-state、output 的 `snapshot_id` 與 `manifest_sha256`，須等於 `checkpoints.json`；`output` 記 `output_id`、`catalog_sha256` 與 `output.json` 的 `files_sha256`；`files` 記維護包內每檔路徑、大小與 SHA-256 |

重產規則：

1. 先核對 `package.json` 的 `files`，再核對兩個快照的 manifest 雜湊等於 `baseline`，並對兩個快照各做一次 `verify_full`。
2. 目前程式的 `config_sha256` 須等於維護包記錄值，否則拒絕。只比對程式與 `uv.lock` 的雜湊，不要求 Git commit 相同。
3. 只用維護包內的檔案執行 `write_output`、`write_catalog` 與 `verify_output`，不讀 `data/raw/`、`config/sources/`、地址專案或任何重建前產物。
4. 每個輸出檔的 SHA-256 須等於 `output.files_sha256` 才通過。報告記錄作業系統、Python 版本與逐檔結果。
5. 任何不符即失敗並保留差異證據，不自動放寬。若原因是跨平台差異，比對標準由擁有者決定。
