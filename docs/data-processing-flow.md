# 完整資料處理流程

本文件描述新版企劃的資料處理與交接流程。P0 基礎、[P1 逐批轉換](p1-conversion.md)及 [P2 離線定位／月年輸出／公開交接](p2-offline-output.md)已驗收。P3 的第一批真實 TGOS 回傳已匯入並驗證，公開回補停在來源權利門檻。P4 的 T-18 已產生真實地址 patch，T-19～T-20 尚待完成。全歷史量測待 P5。圖中的 `@name` 是職責標記，實際狀態以階段紀錄為準。tasks 與 test points 以[完整企劃](drafts/taiwan-lvr-geodata-完整企劃.md)為準。

第一版 output 在離線地址處理後交付，公開於 GitHub。下載以交易月份 `tx_yyyymm` 為最小時間單位，保留 `YYYYMM_category` 命名，再提供年度 ZIP。TGOS 後續補齊受影響月份及年度包。首次重建不匯入舊 SQLite、舊 output 或 migration 座標。

## 圖例與閱讀方式

| 標記 | 意義 |
| --- | --- |
| `(start)` | 一輪工作、一筆記錄或一個地址的入口 |
| `[動作]` | 資料處理步驟 |
| `{ 條件? }` | 有標示結果的分支 |
| `~~▶` | 人工、延後或跨專案交接 |
| `(end √)` | 這個子流程正常完成 |
| `(end >>|)` | 有意保留、排除或等待，不代表永久放棄 |
| `(end ×)` | 拒絕或失敗，保存診斷及前版資料 |
| `@name` | 負責該步驟的模組職責，實作／待辦狀態見階段紀錄 |
| `圖 N` | 子流程接續位置；同一圖只描述一個流程 |

## 圖 1：一輪資料工作的完整主線

```text
(start) 本輪資料工作
  │
  ▼
{ 從 GitHub 離線／回補快照接續? }
  ├── 是 ──▶ [驗證版本、雜湊及維護狀態] @snapshots
  │             │
  │             ▼
  │           { 快照相容且狀態完整? }
  │             ├── 否 ──▶ (end ×) 拒絕接續，保留診斷
  │             └── 是 ──▶ (end √) 依 task 接續圖 3–9
  │
  └── 否 ──▶ [固定 raw 清單與地址來源版本] @sources
                │
                ▼
              { 資源檢查通過? }
                ├── 否 ──▶ (end >>|) 分批／換可用環境後重試
                │
                是
                ▼
              [取得並驗證固定輸入] @sources
                │
                ▼
              [Parse／Normalize，保存來源關聯] 圖 2
                │
                ▼
              [建立全域地址池與離線定位] 圖 3
                │
                ▼
              [建交易幾何，保留未定位記錄] 圖 4
                │
                ▼
              [交易月檔、年度包與維護狀態] 圖 5
                │
                ▼
              [驗證附件並提交 GitHub 指標] 圖 9
                │
                ▼
              (end √) 首版公開 output，不等待 TGOS
                │
                └── 後續增補 ~~▶ 圖 6／7
```

首次資料工作可處理明確的來源子範圍。來源涵蓋不完整時，月／年 manifest 如實標示，不宣稱整月、整年或全歷史完整。Parse-only 表格是內部階段快照。既有快照可接續離線重查、重新輸出、TGOS 或地址 patch；只有快照缺少重建所需資訊時才回到 raw。

## 圖 2：raw ZIP 中一筆記錄的解析與正規化

```text
(start) 清單中的一份 raw ZIP
  │
  ▼
{ 雜湊、ZIP 與成員檢查通過? } @ingest
  ├── 否 ──▶ (end ×) 缺失／損壞診斷，不當成空批次
  │
  是
  ▼
{ 已記錄為已知空批次? }
  ├── 是 ──▶ (end √) 記錄零交易，不編造月份
  │
  否
  ▼
[逐列讀取交易，跳過標頭／英文說明列] @ingest
  │
  ▼
{ 該列可解析? }
  ├── 否 ──▶ (end ×) 保留來源列與失敗診斷
  │
  是
  ▼
[保留 raw_record_id、原值及未知欄位] @ingest
  │
  ▼
[補字、日期、金額單位及地址正規化] @normalize
  │
  ▼
{ 記錄去向? }
  ├── 土地／純車位 ──▶ (end >>|) 保存排除結果及筆數
  ├── 無門牌 ──▶ (end >>|) 保存無門牌結果及覆核資訊
  ├── 日期無效 ──▶ (end >>|) 保存日期診斷，不造月份
  │
  └── 可處理 ──▶ [保存觀測與獨立地址成員] @normalize
                    │
                    ▼
                  { 地址仍缺字／展開歧義? }
                    ├── 是 ──▶ (end >>|) 保存待補正觀測，保留 null
                    └── 否 ──▶ (end √) 成員進入圖 3
```

缺字或地址展開歧義的觀測保留在首版輸出，幾何維持 null 或依已定位成員標為 partial；人工補正後重新評估。無法安全展開時不猜測地址成員。

每個來源交易列只有一種保留／排除／失敗去向。診斷可與保留記錄重疊，但不能多算交易。金額存於觀測或已驗證交易列，地址展開不複製金額。

交易識別尚未證明時，保留來源觀測粒度及空 `transaction_key`。有來源證據才能合併交易或選修訂，不以下載時間或相似欄位推定。

## 圖 3：一個地址鍵的離線定位

```text
(start) 全域池中的 key_version／building_key
  │
  ▼
[保留村里／子門牌，使用 v2 結構鍵] @address
  │
  ▼
{ 鍵與行政範圍可確定? }
  ├── 否 ──▶ (end >>|) 地址診斷／覆核，不播入座標
  │
  是
  ▼
[核對舊狀態證據與固定地址來源] @offline_lookup
  │
  ▼
{ 可信座標／來源證據衝突? }
  ├── 是 ──▶ (end >>|) 衝突覆核，不取 CSV 第一筆
  │
  否
  ▼
{ 有有效 exact／已驗證別名結果? }
  ├── 是 ──▶ (end √) 附證據定位全部適用觀測
  │
  否
  ▼
[固定版門牌索引查詢與補字候選驗證] @offline_lookup
  │
  ▼
{ 查詢結果? }
  ├── 唯一有效 ──▶ (end √) 地址結果供圖 4／5 使用
  ├── 歧義／不同座標 ──▶ (end >>|) 隔離覆核
  └── 無結果 ──▶ (end >>|) 未定位池，交圖 6 選候選
```

來源 commit 改變時，重新核對離線來源定位，移除或衝突的證據不能直接沿用。地址家族只用於排程，鄰近座標或相似道路不證明同一門牌。

全域池在已宣告輸入範圍內跨年份與 sales／presale／rent 去重。來源關聯另存 `address_occurrences`，避免單鍵聚合無上限的清單。

## 圖 4：一筆輸出記錄的幾何

```text
(start) 交易／來源觀測與地址成員結果
  │
  ▼
[依證明的識別粒度取列，金額只計一次] @export
  │
  ▼
{ 不同已定位座標數? }
  ├── 零 ──▶ (end √) null geometry＋未定位診斷
  ├── 一 ──▶ (end √) Point
  │
  └── 多個 ──▶ { category 是 rent? }
                 ├── 是 ──▶ (end √) MultiPoint
                 │
                 否
                 ▼
               { bbox 寬高皆大於零? }
                 ├── 是 ──▶ (end √) Polygon，明示 bbox 近似
                 └── 否 ──▶ (end √) MultiPoint，避免退化面
```

每筆結果包含已定位／總成員數及 partial 標記。位置成員另表參照，不能在統計重複加總金額。GeoParquet 使用 CRS84 經度／緯度順序與 WKB，三格式保留相同 ID、粒度、筆數及 null。

## 圖 5：一版 output 的月／年包裝與交付

```text
(start) 已完成離線處理或歷史回補的記錄集
  │
  ▼
[依交易 tx_yyyymm 與 category 分月] @export
  │
  ▼
[產生月 GeoParquet／GeoJSON／NDJSON] @export
  │
  ▼
[保留 YYYYMM_category 檔名，驗證三格式] @export
  │
  ▼
[同一快照原月檔組成年格式 ZIP] @packaging
  │
  ▼
[列出已有／缺失／空月份與範圍完整性] @packaging
  │
  ▼
[量測月檔、年包、維護狀態與暫存] @measure_output
  │
  ▼
{ 檔案需技術分片? }
  ├── 是 ──▶ [列全部分片與重組索引] @packaging
  │             │
  │             ▼
  │           (end √) 月／年邏輯單位完整，交圖 9
  │
  └── 否 ──▶ (end √) 月獨立檔＋年度包，交圖 9
```

GitHub 下載索引提供年／月／類別／格式的 URL、大小與 SHA-256。一般產物及維護狀態使用公開 Releases，小型固定檔案依實測安排 Git。

使用者只需一個月時，下載該月所需類別／格式，不必下載年包、raw 或全部維護狀態。年度 ZIP 內的月檔須與獨立月檔逐位元組相同。部分年度或來源範圍明確標示，不把缺月當成零筆。

回補改變某月後，只重建受影響月份與對應年度包。未變月檔可沿用已驗證雜湊，年度包依單一快照宣告版本組成。

## 圖 6：一輪 TGOS 候選、配額及人工交接

```text
(start) 最新已提交快照的未定位地址池
  │
  ▼
[排除已定位、衝突、保留及提交不明鍵] @tgos.prepare_tgos
  │
  ▼
{ 相同查詢已送過? }
  ├── 是 ──▶ { 有核准重試／已驗證新表示? }
  │             ├── 否 ──▶ (end >>|) 留池等待，不原樣重送
  │             └── 是 ──▶ (end √) 有原因的新候選
  │
  └── 否 ──▶ (end √) 首次候選
```

上圖兩種候選合併後，再走以下單輪流程：

```text
(start) 本輪合格候選
  │
  ▼
{ 本輪還有合格候選? }
  ├── 否 ──▶ (end >>|) 保留最新狀態，不產生空 CSV
  │
  是
  ▼
[按 address_family 與固定順序選取] @tgos.prepare_tgos
  │
  ▼
{ 共用帳號今日尚有配額? }
  ├── 否 ──▶ (end >>|) 等待，不預建未來日期批次
  │
  是
  ▼
[選不超過剩餘配額，單片最多 10,000 資料列] @tgos.prepare_tgos
  │
  ▼
[先提交保留帳本與 batch manifest] 圖 9
  │
  ▼
{ 提交成功? }
  ├── 否 ──▶ (end ×) 不交付 CSV，依新 parent 重算
  │
  是
  ▼
[輸出 UTF-8-sig CSV；地址列與 manifest 對照] @tgos.prepare_tgos
  │
  ▼
[人工 addrCompare 上傳，確認提交] ~~▶ 操作員
  │
  ▼
{ 操作員回報? }
  ├── 提交前取消 ──▶ (end >>|) 記取消並釋放保留
  ├── 不確定 ──▶ (end >>|) 保留配額，人工核對
  └── 確認提交 ──▶ (end √) 等通知／下載，接圖 7
```

沿用舊操作文件：共用帳號每日最多 10,000 筆，每片最多 10,000 行。座標系選擇 WGS84 經緯度 EPSG:4326。在 addrCompare 的「模糊比對規則設定」區塊開啟「分單／雙號比對」，誤差選擇「不限」，回傳筆數選擇「僅回傳一筆」，其餘選項不勾選。

不為不同 agent 分配互不知情的獨立配額。家族超過上限時按固定順序拆分，不增加額度。提交確認、取消及保留都經圖 9 的 parent／寫入保護。提交確認需核對操作員服務日期及當日配額。提交不明不因逾時自動釋放，等待人工時釋放 cloud runner。

```text
(start) 人工下載的 addrCompare 完成 CSV
  │
  ▼
[保存為 data/tgos/BATCH_ID/response.csv] ~~▶ 操作員
  │
  ▼
[保存原回傳與雜湊，取得原批次 manifest] @tgos.import_tgos
  │
  ▼
{ 同批次／雜湊已匯入? }
  ├── 是 ──▶ (end >>|) 不重複記錄，沿用已驗證結果
  │
  否
  ▼
{ Address 可精確一對一對照? }
  ├── 否 ──▶ (end ×) 拒絕匯入，不當成查詢失敗
  │
  是
  ▼
{ 回傳與座標證據? }
  ├── 查無結果 ──▶ (end >>|) 保存嘗試，留未定位池
  ├── 軸／CRS／門牌不確定 ──▶ (end >>|) 保存觀測供覆核
  │
  └── 有效 ──▶ [保存觀測，驗證完整門牌／別名] @address_state
                 │
                 ▼
               { 證據衝突／別名循環? }
                 ├── 是 ──▶ (end >>|) 留衝突，不傳播座標
                 │
                 否
                 ▼
               [更新索引，回補全部適用歷史] @backfill.backfill_output
                 │
                 ▼
               [重建受影響月／年 output] 圖 4／5
                 │
                 ▼
               [提交一份完整子快照] 圖 9
                 │
                 ▼
               (end √) 新快照生效
                 │
                 ├── 下一輪 ~~▶ 重算全部未定位池，回圖 6
                 └── 地址回補 ~~▶ 圖 8
```

查無、覆核及衝突結果也保存到已驗證子快照，不能只保存成功結果。晚到結果依相同證據規則處理。Response_Address 相同或座標相近，不足以證明別名。

匯入必須有 Address、Response_Address、Response_X、Response_Y 欄位。依 Address 對照原查詢，不要求服務回傳 id。缺批次清單或對照歧義會拒絕匯入，不以舊 building_key 截斷子門牌來匹配。失敗查詢仍保留，新表示或明確重試可重新評估。

人工撤銷別名或更新來源證據時，也經歷史回補／受影響月年重建產生子快照，保留前版供復原。第一批真實 TGOS 已匯入。4,871 筆中有 4,428 筆成功、390 筆查無座標、53 筆拒絕。公開回補因未證明 legacy 地址座標可再散布而停止，沒有產生或發布候選。

## 圖 8：一份地址 patch 的跨專案回補

```text
(start) 已驗證門牌級定位觀測
  │
  ▼
{ 地址拆解、行政區與來源證據完整? } @address_patch
  ├── 否 ──▶ (end >>|) 隔離覆核，不編造行政區欄位
  │
  是

[產生 address_patch 與來源 metadata] @address_patch
  │
  ▼
[提交 taiwan-address-data 審查／匯入] ~~▶ 地址專案

  ├── 是 ──▶ (end >>|) 不重複匯入
  │
  否
  ▼
[持久保存 supplements，讀固定基底] @import_lvr_patch
  │
  ▼
[有官方更新才暫存；否則沿用固定基底] @update_addresses
  │
  ▼
{ 本輪基底可用且無未決衝突? }
  ├── 否 ──▶ (end ×) 不提交該輪變更，保留前版
  │
  是
  ▼
[基底＋補充產生 roads，再重建 road.csv] @materialize
  │
  ▼
[驗證 14 欄、代碼字串與前端相容] @materialize
  │
  ▼
[提交明確完整變更，更新固定來源版本] @git
  │
  ▼
(end √) 下一輪主專案明確選取新 commit
```

patch 匯入與官方更新共用寫入控制。匯入可以只重建補充影響的縣市，不要求每次先下載官方更新。既有 roads 由固定版本建立 `legacy_base`，來源未驗證時不宣稱全是官方。

官方更新不得刪除補充成果，也不得讓前端任取衝突 CSV 第一列。不能從含 supplements 的 roads 反推乾淨基底。不自動跨 repo 合併，也不互相循環觸發。
